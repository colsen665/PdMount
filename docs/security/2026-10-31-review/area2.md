## Area 2 (`crates/pdmount-core` and `crates/pdmount-fuse`, M4 changes `m4-start..4903f03`): findings

Reviewed from `git diff m4-start..HEAD -- crates/pdmount-core crates/pdmount-fuse` plus the full current `staging.rs`,
`engine/pins.rs`, `engine/queue.rs` and the engine/journal paths they call. Threat model: `docs/security/threat-model.md`
(D070). Open Lows of the 2026-10-27 review are not repeated unless M4 made them worse (none did).

### B2-1: A pin fetch stops below 1 GiB free only between files; one file larger than the free space fills the disk
- **Rating**: Medium
- **Location**: `crates/pdmount-core/src/engine/pins.rs:508-531` (`pin_round`: `free_disk_bytes() < FREE_RESERVE` checked once per file, before `fetch_pinned`), `pins.rs:546-572` (`fetch_pinned`: one `cache.get` per block, no space check), `pins.rs:25` (`FREE_RESERVE`), `cache.rs` `DiskIndex::insert`/`enforce_cap` (pinned bytes are not counted against `cache.max_bytes`), `cache.rs` `evict_to`/`wipe` (pinned entries are never victims). Design promise: `DESIGN.md:357` "the fetcher stops below 1 GiB free".
- **Actor**: T2 (another device adds or replaces a file inside a folder the user pinned), with the user's pin as the precondition (T5).
- **Attack**: the user pins `Photos/` (10 GB known, 50 GB free). Another device uploads a 60 GB file there. The next pin round passes the free-space check (49 GB free) and `fetch_pinned` downloads block after block, each `put` landing as a pinned row; nothing stops it until `put` fails with ENOSPC. The disk is then full, not 1 GiB short. The blocks already on disk are pinned, so `cache gc` and `cache wipe` do not free them (`evict_to` iterates `by_age`, which holds unpinned entries only; `wipe` filters `!entry.pinned`); only `unpin` frees them. The pin task itself only reaches the "1 GiB free" wait after the failure. With the home file system full, the store's WAL writes fail (D032 replies wait for commits), and every other application of the user fails to write.
- **Impact**: local disk exhaustion from remote input (A5 availability, daemon DoS); recovery needs the user to find and `unpin` the path.
- **Fix**: check `free_disk_bytes() < FREE_RESERVE` per background turn inside `fetch_pinned` (every `BLOCKS_PER_TURN` blocks, or before each `put`); on ENOSPC let the partial revision go (`set_pinned(.., false)` for it, or evict its blocks) so the reserve is restored; optionally refuse to pin a single file whose size exceeds the free space at the time it is first seen. Keep the per-file check for the common case.
- **Confidence**: high on the code path; medium on the rating (the user opted into pins; the gap is the reserved last 1 GiB).

### B2-2: A stale `Staged` writes through the current staging's descriptor and sidecar of the same inode (D063)
- **Rating**: Low
- **Location**: `crates/pdmount-core/src/staging.rs:433-435` (`Staged::file` resolves the descriptor by inode through the shared `FdCache` on every call), `staging.rs:75-84` (`FdCache::get`), `staging.rs:561-580` (`materialize` writes data then `save()`), `staging.rs:667-685` (`save` writes `staging/<ino>.state`, a path shared by every `Staged` of the inode); `crates/pdmount-core/src/engine.rs:2060-2083` (`Engine::materialize` takes the `Arc<StagingLock>` once, releases the lock across the network await and writes into it afterwards without checking it is still the current entry; contrast `with_staged`, `engine.rs:1990-2011`, which does check); unstage sites that can run meanwhile: `engine/queue.rs:570-592` (`discard_local_content`, `queue drop`), `journal.rs:2287-2299` (upload commit, clean), `journal.rs:2128-2134` (`readopt_remote_content`, remote-triggered), `engine.rs:2200-2215` (`drop_detached`).
- **Actor**: T5/T2 timing (a `queue drop`, an upload commit or a remote-triggered readopt while a FUSE write of a partial block is materializing), plus a crash (kill -9) in the window.
- **Attack**: before M4 each `Staged` owned its `File`, so a stale one wrote into its own unlinked inode. Now: (1) a FUSE `write()` on file F (staged, base R1) needs materialization and awaits the block read with the old `Arc` S_old (`engine.rs:2077`); (2) S_old is unstaged meanwhile (user `queue drop`, or the upload of F commits clean, or a remote identical revision readopts) and the next FUSE operation on F stages anew: S_new with base R2, fresh sidecar (`create`, `staging.rs:330`), truncated data file and a replaced descriptor; (3) S_old's `materialize` resumes: its own `base` check passes (R1 == its own sidecar), `file()` returns S_new's descriptor, so R1's block lands in S_new's data file, and `save()` overwrites S_new's sidecar on disk with S_old's (base R1, `base_rev` R1, `materialized {i}`). In memory S_new is right and its next save repairs the disk; a crash before that leaves a data file of S_new with a sidecar of S_old. After the restart `reopen` builds on R1 with R2's size, and the upload uses base_rev R1.
- **Impact**: after the crash the file is rebuilt from a mix of R1 and R2 content; the upload has the wrong precondition, so it ends as a conflict copy rather than a silent overwrite (A4 integrity, not silent). Without a crash, no effect.
- **Fix**: make a stale `Staged` inert: give each staging a generation (bumped in `StagingDir::create`), key the `FdCache` by `(ino, generation)` and name the sidecar/data by generation, or have `Engine::materialize` re-check `Arc::ptr_eq(self.staged.lock().get(&ino), &staged)` under the staged lock before `materialize`, and make `Staged::materialize`/`save` no-ops once the `Staged` is marked retired (set in `unstage`). The same check is cheap in `setattr_slow`.
- **Confidence**: medium (code path traced; the crash window is short and needs two concurrent operations on one file).

### B2-3: `Journal::start` starts a step for an entry `queue drop` just forgot
- **Rating**: Low
- **Location**: `crates/pdmount-core/src/journal.rs:482-496` (`start`: `None => true`), `journal.rs:846-876` (`run_journal`: `plan()` then `start()`), `journal.rs:664-678` (`hold`), `journal.rs:695-703` (`forget`), `engine/queue.rs:406-450` (`queue_drop`: `hold`, `undo_entry` → `forget`, `release`), `queue.rs:481-505` (`Undo::Delete` mutates the tree, then forgets).
- **Actor**: T5 (`queue drop --yes`) racing the executor.
- **Attack**: the executor's `ready()` lists entry B (a delete, `Plan::Work(Work::Trash)`); `queue drop B --yes` runs `hold([B])` (B not in flight, so it succeeds), `unbind_tombstone(B)` and `forget(B)` between the executor's `plan(B)` (which read the tree before the undo) and `start(B)`. `start` finds no entry and returns `true`, so the trash of B's link is pushed and executed although the user was told "undo the delete; the remote file comes back". For other work kinds the stale `execute(ino, work)` runs likewise; uploads are safe (`try_start_upload` returns `None` without an entry).
- **Impact**: a remote file trashed (recoverable from the trash) or a move/rename executed against the user's explicit drop; one entry, needs sub-millisecond timing.
- **Fix**: `None => false` in `start` (every `start` follows a `ready()` that saw an entry; an entry that is gone was forgotten or done, never to be started), and the same for the trash batch.
- **Confidence**: medium-high on the code, low on the timing being hit in practice.

### B2-4: `entry_path` recurses without a bound over tombstones' remote parent chain
- **Rating**: Low
- **Location**: `crates/pdmount-core/src/engine/queue.rs:100-116` (`entry_path`: recursion on `remote.parent_link` → `by_link` for detached nodes, no depth limit), compared with `queue.rs:119-140` (`entry_within`, which bounds the same walk to `tree.len()` and comments that cycles are possible). Callers: `queue list`/`show` (`queue_entries`), `queue retry`/`park`/`drop` (`queue_items`, `queue_drop`), `sync` (`sync_path`), `parked()` views.
- **Actor**: T2 (remote moves while local deletes are pending) then T5 (`pdmount queue list`).
- **Attack**: two tombstones whose stored `remote.parent_link` name each other (A was deleted locally while under B; B was moved under A remotely before A's trash ran, then deleted locally): `entry_path(A)` → `entry_path(B)` → `entry_path(A)` … until the stack overflows. A stack overflow aborts the process (no `catch_unwind`), so the daemon dies and the mount answers ENOTCONN.
- **Impact**: daemon crash on a queue command; local state is in the store, so no data loss beyond the pending uploads resuming at the next mount.
- **Fix**: iterate with the same `0..=tree.len()` bound as `entry_within` (or a `HashSet` of visited inodes) and fall back to `(inode N)`.
- **Confidence**: medium on the code, low-medium on whether a cycle can arise in the tree (events may rewrite a tombstone's `remote` first).

## Checked and fine (area 2)
- **Staging descriptor LRU (D063)**: `FdCache` keyed by inode; inode numbers are never reused (`allocate_ino` from a durably reserved range, `next = reserved + 1` with `reserved = max(stored rows, ino_reserved)`, `engine.rs:369-370`, `:2638-2646`, `:2900-2910`); staging paths are built from inode numbers only; `create` truncates the data file and replaces the descriptor, `remove` closes it before unlinking; a descriptor evicted while an operation holds its `Arc` still names the same inode; the delayed removal (`remove_committed_staging`, `engine.rs:274-296`) and `stage()` (`:2013-2056`) serialize on the staged map lock, so a removal never deletes a staging created after it. Opens use `O_CLOEXEC`, files 0600 in a 0700 directory.
- **New files without a sidecar (D067)**: a file with a base gets its sidecar before its data file (`staging.rs:322-338`); a default staging removes a stale sidecar first; `staged_inos` removes sidecars without a data file; `reopen` finishes a truncate cut short by a crash (`:377-385`); `set_base_rev` after an upload or an adopt-on-replace writes the sidecar, so a precondition is never lost; `load` drops staging of clean or gone nodes (`engine.rs:2920-2957`). No path leads data to another file (see B2-2 for the one stale-writer hazard).
- **Cache (`cache.rs`)**: M4.0.2.3 bounds intact: `Layout::new` rejects a block above 4 MiB, an empty non-last block and a sum other than the file size with `Integrity`; `BlockCache::get` refuses `expected_len > MAX_BLOCK_BYTES` before allocating; pins and `fetched_of` size reads only through layouts. Keys bind link, revision and index, so no block is served for another revision or file; AAD unchanged. Eviction, `gc` and `wipe` delete only `self.path(key)` under `blocks/`; protected (staged bases) and pinned entries are skipped; a read in progress keeps its open descriptor, and a missing file is a miss. The sweep walks only `blocks/00..ff`, uses `DirEntry::metadata` (no symlink following; `is_file()` is false for a symlink), a 2 s mtime grace, and runs once after the store commits. `DiskIndex` counts stay consistent (`insert` removes first); `set_pinned` is parameterized. RAM hits touch the disk entry so hot blocks are not evicted first.
- **Pins (`pins.rs`)**: pinned revisions come from the local tree (link, rev, size), never from a request; `pin` refuses when the known size does not fit; listings go through `ensure_listed_now` behind the background gate; fetches are paced per 16 blocks; a `Failed` round backs off (1 s → 300 s) and the round continues past a failing file. Sizes are the block-sum sizes of `proton.rs:217-236`. `walk` allocates proportional to the in-memory tree. Remark (Info, no finding): a pinned file whose block list fails `Layout::new` is retried every `BACKOFF_MAX` for ever and never parked; only log noise and one `blocks()` call per retry.
- **Queue and journal (D061, D062)**: `hold` refuses while a step runs; `ready`, `start` and `try_start_upload` all skip held, parked and `stopping` entries; `stop_starting` before `shutdown` waits for `idle()` up to `timeouts.shutdown_grace`. `queue drop` plans from the tree: `Undo::Remove` refuses a subtree containing any node with a remote link; `Undo::Delete` refuses when the folder is deleted and not in the plan; `Undo::Revert` refuses names in a swap and takes the staged lock before reverting; forgotten inner nodes have their staging removed via `apply_changes`. User parks survive local changes; `retry` clears them. `sync_round` bounds its dependency walk (`MAX_DEPENDENCY_CHAIN`). The durable relist queue (D069) stores inode numbers as a space-separated `meta` value with a parameterized `meta_set`, parsed with `parse().ok()` and filtered against the tree.
- **`EngineOptions::read_only` / `-o ro`**: `ensure_writable` returns `ReadOnly` first (`engine.rs:2293-2296`) and is on every mutating entry: `create`/`mkdir`/`remove`/`rename` (`ensure_dir_writable`), `rename` target, `setattr` (any non-empty change), `open_file` with write, `write_local` (also for handles opened earlier), `access` with `MAY_WRITE`; `masked` strips write bits; `mknod`, `symlink`, `link` answer EPERM, `setxattr` ENOTSUP, `fallocate` is a write path; `MountOption::RO` is passed to the kernel too. The journal still uploads pending work in `ro`, as the option's documentation states (`engine.rs:112-113`). The control-socket actions (`queue`, `pin`, `cache`) change local state only.
- **`fsync.remote_paths`**: compiled with `globset` and `literal_separator(true)` at `Config::validate` and at `Engine::open`; matching is automaton-based (linear in the path), run against the tree path of the inode; `fsync_is_remote` short-circuits when the set is empty.
- **Config parsing**: `deny_unknown_fields` kept; `upload.concurrency` bounded 1–4 (D033); `stats.prometheus_textfile` must be absolute or `~/` (the writer lives in `crates/pdmount`, outside this area); `kernel.writeback_cache` removed.
- **Metrics, events, rows, store**: histograms use `saturating_record` with `u64::try_from(micros)`, so remote-driven durations cannot panic; `TimedBackend` is a pass-through; `rows.rs` and `cache.rs` moved to `prepare_cached` with the same parameterized statements; `Store::after` waiters are drained under one lock and closed on writer exit; `events.rs` only records `last_poll`.
- **FUSE layer**: every callback still runs under `catch_unwind` with a `Stopwatch`; D031 checks remain in `opendir` (`MAY_READ`), `open_file`, `setattr` (size without a writable handle), `access`, and the directory-changing operations; `KILLPRIV`/`KILLPRIV_V2` are not requested (D068), the mount is `nosuid`, and the kernel clears setuid/setgid through `setattr`, which bumps the meta generation. Directory pages are kept (D072) only when the entry digest (ino, kind, name) equals the one last served and no other handle is open; remote changes additionally send `inval_inode` for the directory (`vfs.rs:520-532`, `lib.rs:1041`), so a digest collision could not serve stale names.
- **Secrets**: nothing in the diff logs tokens or passphrases; the new `sdk_key_store` path (D085) is only a path.
