Reviewed read-only at commit 4903f03, `git diff m4-start..HEAD -- crates/pdmount`: control.rs, queue.rs, cache.rs, pins.rs, stats.rs, autostart.rs, daemon.rs, secret_cache.rs, session.rs, credentials.rs, auth.rs, notify.rs, status.rs, main.rs, plus `crates/pdmount-core/src/{paths,config}.rs` and `engine/queue.rs` for what the socket requests reach, and the SDK fork checkout `~/.cargo/git/checkouts/proton-sdk-rs2-<hash>/2ae4aa3/` for the secret cache (`crates/proton-drive-sdk/src/cache/sqlite.rs`, `crates/proton-sdk-rs2/src/session.rs`). ### B1-1: The Prometheus textfile's temporary file follows a planted symlink in a shared collector directory
- **Rating**: Medium
- **Location**: `crates/pdmount/src/stats.rs:218-228` (`write_atomically`: `std::fs::write(&temp, text)` on the fixed name `.<name>.tmp`, then `rename`); path from `[stats] prometheus_textfile` (`crates/pdmount-core/src/config.rs:366-369`, any absolute path); run every 15 s from the daemon (`stats.rs:187-214`, `daemon.rs:395-397`).
- **Actor**: T1 (other local user), with T5 (the user points the textfile at a shared directory)
- **Attack**: The textfile is meant for a node_exporter collector directory shared by several writers (DESIGN §5.8: "several profiles can share a collector directory"). Where that directory is group- or world-writable without the sticky bit (or `fs.protected_symlinks=0`), another user creates `.<name>.tmp` as a symlink to any file the victim can write (a shell startup file, an SSH configuration file, a file in the mount). `std::fs::write` opens with `O_CREAT|O_TRUNC` and no `O_EXCL`/`O_NOFOLLOW`, so the daemon truncates the target and writes the metrics text into it; the following `rename` then moves the symlink over `<name>.prom`, and 15 s later the attacker plants the next one. The temporary name is predictable (the config example and the user guide name the file), and the daemon repeats the write for as long as it runs.
- **Impact**: A5: files outside PdMount's directories destroyed (overwritten with fixed metrics text) by another local user. The content is not attacker-chosen and the precondition is a shared-writable non-sticky directory, which keeps this below Critical.
- **Fix**: Create the temporary file with `OpenOptions::new().write(true).create_new(true).custom_flags(libc::O_NOFOLLOW).mode(0o644)` under a random name (`tempfile::Builder::new().prefix(".<name>.").tempfile_in(dir)` then `persist`), and refuse (log once) if the directory is writable by others (`stat` the parent: group/other write bit without the sticky bit); say so in DESIGN §5.8 and the user guide. `rename` itself is fine.
- **Confidence**: high that the code follows a symlink; medium on the precondition being met in real deployments.

### B1-2: An autostart entry for a profile that was never logged in sends the sign-in link to the session's stdout log
- **Rating**: Low
- **Location**: `crates/pdmount/src/autostart.rs:47-51` (Exec is `pdmount --profile <p> [flag] mount`, without `--no-login`); `crates/pdmount/src/daemon.rs:175-188` (`mount_background`: no stored credentials → `session::login` in the CLI process); `crates/pdmount/src/session.rs:113-131` (`present_link` writes the URL to stdout; `should_open_browser(Auto, interactive=false, …)` is false, so no browser and no notification either).
- **Actor**: T4 (same-uid process logs); T1 where the display manager keeps the X session log world-readable (no systemd user journal on this Gentoo/OpenRC host).
- **Attack**: The user runs `pdmount autostart enable` before the first `pdmount login` (or after `logout`, or after a cache-key loss deleted the credentials). At the next desktop login the entry runs `mount`; `Credentials::load()` is `None`, so the CLI starts the web login and prints "Open this link to sign in: https://account.proton.me/…#<fork key>" to stdout, which the session manager redirects to its log (the X session log, the user journal) or `/dev/null`. The link waits there 10 min. D071 and DESIGN §12.2 route the headless case through the daemon (`status` over the 0600 socket, code-only log) precisely to keep the link out of logs; this path bypasses it. The user never sees anything (no terminal, no browser, no `notify-send`).
- **Impact**: Half of the fork secret in a log file whose mode PdMount does not control; the login also blocks the autostart process for 10 min. Only for a profile without stored credentials, so an edge case.
- **Fix**: `mount_background` should not run the interactive login when stdout is not a terminal (`!interactive()`): fail with "profile <p> is not logged in; run `pdmount login`" and send the `notify::desktop` notice; or have the autostart entry pass `--no-login` (DESIGN §12.2 already defines that flag for scripts). Document in §14.2.
- **Confidence**: high that the link reaches stdout; medium on the exposure (depends on the display manager).

### B1-3: Key passphrases of a refused or unstorable login stay in `sdk-keys.db` for good
- **Rating**: Low
- **Location**: fork `crates/proton-sdk-rs2/src/session.rs:319-324` (the web login writes `account:passphrase:<key id>` for every key of the signed-in user before it returns); `crates/pdmount/src/auth.rs:269-276` (`adopt` refuses another account and calls `end_unstored`); `crates/pdmount/src/session.rs:160-173` (`store_login` failure also ends the session); `crates/pdmount/src/session.rs:176-180` (`end_unstored` only ends the server session); `crates/pdmount/src/secret_cache.rs:57-59` (`clear` keeps passphrases; the SDK never calls `clear` on the secret cache anyway: no caller in the fork).
- **Actor**: T4 (hygiene of A1 material at rest)
- **Attack**: A daemon in `needs_login` gets a sign-in by a different Proton account (a family member's, a work account) and refuses it; or the keyring prompt is dismissed, so the new session cannot be stored and is ended. In both cases the passphrases of the keys of that account are already in `sdk-keys.db`, sealed with the profile's cache key, and nothing removes them: not `end_unstored`, not the next login (different key ids), not eviction (D085 removed it; before D085 they left the 5000-entry cache eventually). Only `logout` or a new cache key deletes the file.
- **Impact**: Key material of a session that no longer exists persists indefinitely in the profile's data directory (0600, encrypted with a key from the keyring or `cache.key`). Useful to an attacker only together with that account's armored private keys, so Low.
- **Fix**: On `end_unstored`, remove the passphrase entries the login just wrote: iterate the user's key ids (`user.keys` are known to the session) and `remove("account:passphrase:<id>")` on the secret cache; or have `begin_web_login` hand back the ids. Add a test next to `the_passphrase_outlives_eviction`.
- **Confidence**: high

### B1-4: Minor hardening (Info)
- `daemon.rs:131-143`: `rotate_log` renames the old log to `<profile>.log.1` with the mode it had; `open_log` (`:145-161`) restores 0600 only on the current log. The one case of a 0644 `.log.1` is the first large pre-M4.0.2.1 log rotated after the upgrade (it may hold the sign-in links the old version logged, A1-2), but `open_log` makes the directory 0700 in the same call, so other users cannot reach it. Chmod the rotated file too.
- `autostart.rs:65-70`: the entry is written with `std::fs::write` (umask mode, 0644 in a default 0755 `~/.config/autostart`) and names the binary path and the secret-storage flag (`--allow-file-secrets`/`--force-file-secrets`), so other users learn where this user keeps Proton secrets. Not secret, but 0600 costs nothing. `current_exe()` is persisted as resolved through `/proc/self/exe` (a build directory, if that is where it ran from); `enable` could warn when the path is under `target/` or a temporary directory.
- `stats.rs:226`: the textfile has the umask mode; its content is counters, gauges and fixed op names only (no remote names; the only label from outside is the restricted profile name, escaped at `:179-184`). Fine as is once B1-1 is fixed.
- `secret_cache.rs:87`: `ATTACH DATABASE ?1` on a connection opened by `rusqlite::Connection::open`, whose default flags include `SQLITE_OPEN_URI`, so the key store's path is URI-parsed when it starts with `file:`. The path comes from `$XDG_DATA_HOME` (T5 only); pass `OpenFlags` without `SQLITE_OPEN_URI` or open with `open_with_flags`.
- `secret_cache.rs:88-96`: the move is one transaction over two WAL databases (the SDK sets `journal_mode = WAL`, fork `cache/sqlite.rs:239`), which SQLite does not commit atomically across files. A crash between the two commits leaves either a duplicate (harmless, `INSERT OR IGNORE` next time) or a passphrase deleted from `sdk-secrets.db` before it reached `sdk-keys.db` (one more login). Copy first, commit, then delete in a second transaction.
- `queue.rs:165`: `pdmount sync --timeout 18446744073709551615` panics the CLI in `Duration + SYNC_MARGIN` (T5, same family as S-16); use `saturating_add`.

## Checked and fine (area 1)
- Control socket unchanged in what matters: directory 0700 (`control.rs:528-537`), socket chmod 0600 after bind (`:546`), peer uid checked before the first read (`:569-573`); every new request (`QueueList/Retry/Park/Drop`, `Sync`, `CacheStats/Gc/Wipe`, `PinSet/Unset/List`, `Stats{reset}`) is a typed `serde` variant; a bad request answers `ok:false` and never panics the daemon.
- `queue drop`: the CLI requires `--yes` (`main.rs:899-901`); the engine with `yes:false` only reports (`engine/queue.rs:397-405`), with `yes:true` takes `journal.hold` and refuses as a whole while a step runs (`:406-411`), and restores the pre-change tree listing before reverting. `queue retry/park` change schedule state only. Paths from the CLI go through `access::mount_relative` (rejects `..` and outside paths); over the socket they are resolved against the inode tree, never joined to a local path.
- `cache wipe`/`cache gc`: cache-only, pinned blocks and protected base revisions are kept (`cache.rs:1-3`, `daemon.rs:923-938`); no data loss possible. `stats --reset` clears latency histograms only (`stats.rs:33-35`).
- Autostart Exec quoting: the reserved set (`autostart.rs:21`) matches the Desktop Entry spec, `%` is doubled before quoting, `"`, `` ` ``, `$`, `\` are escaped inside quotes, and `escape_value` applies the string escapes on top (`:39-45`), so a quoted backslash is four in the file, as in the spec's example; profile names are `[a-z0-9][a-z0-9_-]{0,63}`; `\n`, `\t`, `\r` in the binary path are quoted and escaped. No shell is involved at any layer.
- `sdk-keys.db` (D085): opened like the other caches: parent `create_private_dir` (0700) first, then `open_file`, then 0600 on the db and `-wal`/`-shm` (`session.rs:42-55`, `:66-72`); side files SQLite creates later inherit the db's 0600 (unix VFS copies the main file's mode), inside a 0700 directory. The move runs after both stores exist and before any `set`, and eviction happens only in `set` (fork `cache/sqlite.rs:74-100`), so the passphrase cannot be lost between open and move. `logout` removes it with its side files (`session.rs:455-470`), a new cache key deletes it (`credentials.rs:420-453`), `reset --keep-login` keeps it by design. The SQL binds parameters; the prefix `account:passphrase:` matches the SDK's key format (test goes through the SDK's own `SessionSecretCache`).
- M4.0.2.1 intact: the log is opened 0600 in a 0700 directory, both set again on every background mount (`daemon.rs:145-161`, test `the_log_is_private`); the filter blocks every `proton_sdk_rs2*` record above WARN even with `RUST_LOG=proton_sdk_rs2::account=trace` (`main.rs:528-551`, test `sdk_debug_records_never_reach_the_log`); the daemon inherits only `-v` flags and the secrets flag (`daemon.rs:195-213`). The sign-in link is logged nowhere (`auth.rs:302-322` logs the code only; the error strings from the fork's web login carry no URL), `notify-send` argv is summary and "run `pdmount login`" (`notify.rs:53-55`, test), and the link lives in memory, cleared when the login ends (`auth.rs:222`), handed out only over the socket (`daemon.rs:769-770`, `:713-725`). `pdmount status` and `pdmount login` print it to stdout as designed.
- `rotate_log` runs only in `mount_background` after `preflight` refused a running or stopping daemon, so no daemon writes the file being renamed; the state directory is PdMount's own, 0700, so symlinks there are same-uid only. `log_tail` prints the new daemon's lines to the terminal (code, no link).
- `status.rs`: a resumed session whose keys do not unlock is reported as `needs_login` without opening a login (`status.rs:297-318`); no secrets in the report.
- `BackendChoice::parse` refuses `fake:<dir>` without the `fake-backend` feature (`daemon.rs:64-85`); `FakeCommand` (`fake profile`, faults) is `#[cfg(feature = "fake-backend")]` in `main.rs`.
