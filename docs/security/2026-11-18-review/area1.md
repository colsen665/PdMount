## Area C1 (release pipeline and build supply chain): findings

Reviewed read-only at commit `9818aa1`. Files: `.github/workflows/ci.yml`, `.github/workflows/release.yml` (generated by
dist 0.32.0), `.github/build-setup.yml`, `dist-workspace.toml`, `Cargo.toml` (`[patch.crates-io]`, `[profile.dist]`),
`Cargo.lock` (608 packages: 602 from crates.io with checksums, 2 from the fork by full commit, 4 workspace members),
`about.toml`, `about.hbs`, `THIRD-PARTY-LICENSES.html`, `scripts/ci.sh`, `scripts/build-doctor.sh`, `private_root` and
`remove_fake_dir` in `tests/scenarios/lib.sh`, `.betterleaks.toml`, `.betterleaksignore`, the install section of
`docs/user-guide.md`, the "Release" section of `AGENTS.md`, and `docs/security/threat-model.md` ("Build-time supply chain").

Dependencies read: `gopenpgp-sys` 0.3.9 (`build.rs`, `go/go.mod`, `go/vendor/`), `openssl-src` 300.6.1+3.6.3 (`src/lib.rs`),
`openssl-sys` 0.9.117 (`build/find_vendored.rs`), `libsqlite3-sys` 0.37.0 (`build.rs`, the bundled SQLCipher source for
OpenSSL provider and engine calls), the fork's two `build.rs` and its workflows at `pdmount-0.5` (`70f10ff`). The build
scripts of all locked crates whose sources were on disk (87 scripts of 603 crates) were searched for download commands.
The option names of dist were read from the strings of a local `dist` 0.32.0 binary. A local release binary that already
existed under `target/release/` was searched for embedded paths (nothing was built).

Not covered:
- No network was used. The GitHub settings (rulesets, tag and branch protection, immutable releases, Actions approval,
  default token permission, whether Actions are enabled on the fork), the published v0.5.0 assets and the log of its
  release run were not looked at. Where a finding depends on them, it says so.
- The scanner's private rule file was not read, so C1-7 rests on the gitleaks-compatible meaning of `[[allowlists]]`.
- dist's own source was not read; "dist does not pass `--locked`" (C1-4) comes from the binary's strings only.
- `scripts/repro/`, `scripts/bench/`, `tests/scenarios/*.sh` other than the two helpers named above.
- Advisories for the locked crates (out of scope per the threat model).

The threat model already records as accepted or not done: actions by major tag in `release.yml`, the dist installer
without a hash check, unpinned apt packages, Go `1.25.x`, no signatures or attestations, and that the `.sha256` proves
integrity only. Those are not repeated as findings; C1-2 and C1-5 report that two of those acceptances rest on a premise
that no longer holds for dist 0.32.0.

No Critical, High or Medium finding. The ratings below use the threat model's scale, which has no asset for the
published release or the repository; if the verifier adds one (see "Threat model: what is missing"), C1-1 would be the
candidate for Medium.

## Findings

### C1-1: Every build script of the release build gets a token that can write to the repository and its releases

- **Rating:** Low
- **Location:** `.github/workflows/release.yml:17-18` (workflow-wide `contents: write`), `:112-113` (`GH_TOKEN` in the
  job environment of `build-local-artifacts`), `:148-150` (`dist build`, which runs cargo and with it every `build.rs`
  and proc-macro); the same token in `plan` (`:56-57`), where the dist installer script runs (`:67`).
- **Actor:** not in the threat model: a compromised build input (a crate's build script or proc-macro, the Go toolchain,
  an apt package, the dist installer or an action referenced by tag).
- **Scenario:** a `v*` tag is pushed. One of the 87 build scripts or a proc-macro of the 600 locked crates is malicious
  in the locked version. It reads `GH_TOKEN` from its environment. With `contents: write` it calls the GitHub API to
  delete the asset `pdmount-x86_64-unknown-linux-gnu.tar.gz` and its `.sha256` from the existing v0.5.0 Release and
  upload replacements, and pushes a commit to `master` (source files; the token cannot change workflow files).
- **Impact:** such a build input can alter the archive it is building in any case. The token adds what it could not do
  otherwise: replace the assets of earlier Releases together with their checksums (undetectable for a user, since the
  checksum comes from the same place), move or create tags, and change the source on `master`. The changes outlast the
  job although the token expires with it.
- **Fix:** three settings on GitHub, no workflow edit: (1) immutable releases for the repository, so that a published
  Release's assets and tag cannot be changed; (2) a branch ruleset on `master` and a tag ruleset (pattern: see C1-3)
  without a bypass for GitHub Actions; (3) default workflow permissions read-only. In the workflow, only `host` needs
  `contents: write`; dist generates the workflow-wide grant, so narrowing it needs `allow-dirty = ["ci"]`, which D097
  avoids. Record the residual in the threat model.
- **Confidence:** high for the token's presence and scope in the file. Whether a ruleset or immutable releases already
  limit it was not checked (settings).

### C1-2: The actions of `release.yml` can be pinned by commit through dist's own configuration

- **Rating:** Low
- **Location:** `.github/workflows/release.yml:59`, `:69`, `:85`, `:119`, `:139`, `:166`, `:183`, `:188`, `:195`, `:213`,
  `:233`, `:238`, `:245`, `:258`, `:265`, `:298` (`actions/checkout@v6`, `actions/upload-artifact@v7`,
  `actions/download-artifact@v8`); `dist-workspace.toml:6-25` (no `github-action-commits`);
  `docs/security/threat-model.md:129-132` ("Accepted: pinning would need `allow-dirty = ["ci"]` and hand edits").
- **Actor:** a compromised action (a moved major tag), not in the threat model as an actor.
- **Scenario:** the `v6` tag of `actions/checkout` or the tags of the artifact actions are moved to a malicious commit.
  The next tag build runs it in `host` (`:233-265`), the job that creates the Release with the write token; the artifact
  actions also carry the `dist` binary from `plan` to `host` (`:69-72`, `:187-192`) and the archive to the Release.
- **Impact:** code execution in the release job and control of the published archive. The threat model accepted this
  because pinning seemed to need hand edits. dist 0.32.0 has the configuration key `github-action-commits` (present in
  the local binary's configuration schema, next to `github-build-setup`), so the acceptance can be withdrawn at no cost
  to "never edit `release.yml` by hand".
- **Fix:** add `[dist.github-action-commits]` to `dist-workspace.toml` with the full commit of each of the three actions,
  run `dist generate`, and check that `release.yml` then references commits (as `build-setup.yml:4` and `ci.yml:38`
  already do). Update the threat model's paragraph. The installer script at `:67` stays unverified (dist offers no hash
  for it); it is fetched by exact version from dist's Release.
- **Confidence:** high that the key exists in 0.32.0; medium for its exact table format (not tried: nothing was
  generated).

### C1-3: The release starts on far more tags than `v*`, and the tag name is pasted into shell commands

- **Rating:** Low
- **Location:** `.github/workflows/release.yml:43-45` (trigger `'**[0-9]+.[0-9]+.[0-9]+*'`), `:53-54` and `:80`, `:150`,
  `:203`, `:253`, `:284` (`github.ref_name` and the outputs made from it, expanded inside `run:` scripts);
  `docs/security/threat-model.md:145-146` and `AGENTS.md` "Release" (both speak of `v*` tags).
- **Actor:** whoever can push a tag: the maintainer's account, the push key on the development machine (which agents
  and every process of that user can use; T4 in the local model), or a mistake (`git push --tags`).
- **Scenario A (rule bypass, mistake):** the user follows the threat model and restricts `v*` tags with a ruleset. A tag
  `0.5.0`, `pdmount-v0.5.0`, `pdmount/0.5.0` or `backup-0.5.0` is not covered, matches the trigger, and dist accepts
  it when its version equals the workspace version. The tagged commit need not be on `master` or have passed CI. A
  public Release is created from it.
- **Scenario B (injection):** git allows `$`, `(`, `)`, `;`, `|`, `{`, `}` and backquotes in tag names. A tag named
  `v0.5.1$(id)` matches the trigger and line 80 becomes `dist host --steps=create --tag=v0.5.1$(id) …`: the substitution
  runs in `plan` with the write token. `${IFS}` stands in for spaces.
- **Impact:** A: a release that the tag rule was meant to prevent. B: gives nothing to someone who can push to the
  repository freely, but it turns "may create some tag" into "runs commands with `contents: write`", which matters as
  soon as tag creation is restricted by pattern or a second person gets write access.
- **Fix:** make the tag ruleset cover what the trigger covers: restrict creation, update and deletion for the pattern
  `*[0-9].[0-9]*` (or simply all tags, `*`), and document that pattern in the threat model and `AGENTS.md` instead of
  `v*`. The injection is in generated code; a ruleset that only admits `v<digits>.<digits>.<digits>` and the `-rc.<n>`
  form (rulesets take a regex on tag names in organisation plans; on a personal repository use "restrict creations"
  for all tags with the maintainer as the only bypass) removes the hostile names.
- **Confidence:** high for the trigger and the expansion (file content). Medium for which odd tag formats dist then
  accepts; the header comment of `release.yml:20-32` lists `1.0.0`, `my-app/0.1.0` and `releases/v1.0.0`.

### C1-4: The release build runs with neither `--locked` nor the pinned Rust toolchain; the threat model says both

- **Rating:** Low
- **Location:** `.github/workflows/release.yml:123-150` (no Rust install outside containers, `dist build`);
  `.github/workflows/ci.yml:26`, `:49-52` (the pin exists only here); no `rust-toolchain.toml` in the repository;
  `docs/security/threat-model.md:138` ("The Rust toolchain comes from rustup at a pinned version"), `:140` ("`Cargo.lock`
  is checked in and built with `--locked`").
- **Actor:** none needed; a gap between the stated and the actual control. Benefits a compromised newer crate version.
- **Scenario:** (1) a tag is put on a commit whose `Cargo.lock` does not match `Cargo.toml` (for example a version
  bump or a new dependency without the lock update; `ci.yml` would catch it on `master`, but the release does not wait
  for CI and the tag may be on any commit). cargo, called by dist without `--locked`, resolves the missing parts to the
  newest matching versions at build time, which nobody reviewed and `THIRD-PARTY-LICENSES.html` does not list. (2) The
  compiler is whatever stable Rust the `ubuntu-22.04` image carries that week, not 1.98.1, so the released binary is
  built with a compiler the CI never ran.
- **Impact:** an integrity control that the threat model lists does not exist in the release build. With a consistent
  lock file (the normal case, and the case of v0.5.0 if its commit passed `ci.yml`) the lock is honoured anyway.
- **Fix:** two steps in `.github/build-setup.yml`, which dist puts before the build: `rustup toolchain install 1.98.1
  --profile minimal && rustup default 1.98.1` (or a `rust-toolchain.toml` used by both workflows), and `cargo metadata
  --locked --format-version 1 >/dev/null`, which fails when the lock would change. Then correct the two sentences of the
  threat model.
- **Confidence:** high for the toolchain. Medium for `--locked`: the only `--locked` in the dist 0.32.0 binary is an
  installation hint; the v0.5.0 run log would settle it (look at the `cargo build` line).

### C1-5: Provenance can be had from dist's configuration; the user guide presents the checksum as the verification

- **Rating:** Info
- **Location:** `dist-workspace.toml:16` (`checksum = "sha256"`, no `github-attestations`); `docs/user-guide.md:17-25`
  (download, `sha256sum -c`); `AGENTS.md` "Release", step 4; `docs/security/threat-model.md:146-147`, `:150`.
- **Actor:** someone who can replace a Release asset (C1-1), or a user who gets the archive from a mirror.
- **Scenario:** archive and `.sha256` are replaced together; `sha256sum -c` passes. The threat model says this already
  ("integrity of the download, not provenance"); the user guide does not, so a user reads the step as authentication.
- **Impact:** no way for a user to tie the archive to the repository's workflow and commit.
- **Fix:** `github-attestations = true` in `dist-workspace.toml` (the key exists in dist 0.32.0, with
  `github-attestations-phase`); `dist generate` then adds the attestation step and the `id-token: write` and
  `attestations: write` permissions. Add to the user guide `gh attestation verify
  pdmount-x86_64-unknown-linux-gnu.tar.gz --repo <owner>/PdMount` as the provenance check and one sentence that the
  checksum only detects a damaged download. With immutable releases (C1-1) GitHub also records a release attestation.
- **Confidence:** high for the missing step; medium for the generated result (not generated).

### C1-6: `scripts/ci.sh` opens its lock file by a predictable name in `/dev/shm` before the private root exists

- **Rating:** Low
- **Location:** `scripts/ci.sh:148-161` (`exec 9>"$SCENARIO_ROOT.lock"`, with `SCENARIO_ROOT=/dev/shm/pdmount-ci-<cksum
  of the checkout path>`); the check that protects the root itself is `tests/scenarios/lib.sh:60-69` (`private_root`),
  which runs later and does not cover the sibling `.lock`.
- **Actor:** T1 (another local user on the developer's machine).
- **Scenario:** `/dev/shm` is world-writable. T1 knows or guesses the checkout path, computes its `cksum` and creates
  `/dev/shm/pdmount-ci-<n>.lock` first. (a) As a symlink to a file of the developer: `9>` opens with `O_TRUNC` and
  follows it, so the file is emptied, where `fs.protected_symlinks` is 0. (b) As a regular file on which T1 holds
  `flock`: every full CI run in that checkout stops with "another scripts/ci.sh uses SCENARIO_ROOT". (c) With
  `fs.protected_symlinks=1` or `fs.protected_regular>=1` (usual defaults) the open fails and the script ends.
- **Impact:** with the usual sysctls, a denial of the full CI for that checkout until the file is removed by its owner
  or root; without them, truncation of one file the developer can write. This is the pattern S-8 fixed for the root.
- **Fix:** create the root first and keep the lock inside it: call `private_root "$SCENARIO_ROOT"` (source the helper
  or repeat its three lines) and then `exec 9>"$SCENARIO_ROOT/.lock"`; or put the lock under `$XDG_RUNTIME_DIR`.
  Check that no scenario removes the root itself while the lock is held.
- **Confidence:** high for the code path; the effect depends on the two sysctls, which were not read.

### C1-7: Scan exemptions end in `\b`, so they also exempt longer paths under the same prefix, for every rule

- **Rating:** Low
- **Location:** `.betterleaks.toml:4`, `:45`, `:50`, and the `\b`-terminated entries at `:9-15`, `:21-29`, `:39-40`; no
  `targetRules` or `paths` on any `[[allowlists]]` block.
- **Actor:** none; a future commit by the maintainer or an agent that the scan should have stopped.
- **Scenario:** assuming gitleaks' semantics (an allowlist regex is searched, unanchored, in the finding's secret, and a
  block without `targetRules` applies to all rules): a path finding that merely starts with an allowed prefix is dropped.
  Example strings that would pass although they are not the placeholders the descriptions name:
  - `:4` `/home/(?:u|user)\b`: `/home/user.name/<key file>`, `/home/user-backup/keys/deploy`, `/home/u/<key file>`
    (`\b` is satisfied before `.`, `-` and `/`). A real account called `user`, or one starting with `user.` or `user-`,
    is fully exempt.
  - `:45` `/home/runner\b`: `/home/runner-x/…`, and every real path of a machine whose user is called `runner`.
  - `:50` `(?:~|\$HOME)/(?:a|b|x|y|pd|Photos|…|Other|Alone|Home)\b`: `~/pd/<key file>`,
    `~/Other/clients/<name>/contract.pdf`, `~/a-private-project/notes`, `~/Photos/<real album name>/…`.
  - `:24`, `:29` `~/.local/bin\b`, `…/.cargo}?/bin\b`: `~/.local/bin/<private script name>`.
  - `:40` `~/\.config/pdcli\b`: `~/.config/pdcli/<any file name>` (a path, not a file's content).
  Lines 23 and 25 show the tighter form already (`(?:[^/\w.-]|$)`).
- **Impact:** a personal directory name, key file name or project name under one of these prefixes could reach the
  public repository unnoticed. Real tokens are not affected as long as the target is the secret, since a token does not
  contain these path strings.
- **Fix:** end the placeholder patterns with `(?:[^/\w.-]|$)` where no child path is meant (`:4`, `:45`, `:50`), or
  with an explicit list of the children used (`/home/user/(?:photos|docs)\b`); limit `:4` and `:50` to the test and
  documentation files with `paths` and `condition = "AND"`; give each block `targetRules` naming the path rule, if the
  private rule's ID may be written into the repository (ask the user; otherwise leave it).
- **Confidence:** medium: the regex behaviour is certain, the scanner's matching target was inferred, not read.

### C1-8: The release binary carries OpenSSL's engine and module directories as paths under the build directory

- **Rating:** Info
- **Location:** `Cargo.toml:53` (`bundled-sqlcipher-vendored-openssl`), `Cargo.toml:90-95` (`[profile.dist]`: `strip =
  "debuginfo"`, no path remapping); `openssl-src` `src/lib.rs:39`, `:164-200` (`--prefix=<OUT_DIR>/…/install`,
  `--openssldir=/usr/local/ssl`, `no-shared`, `no-module`, engines left on for glibc targets).
- **Actor:** T1, only a local user who owns `/home/runner` on the user's machine (for example the account of a
  self-hosted Actions runner).
- **Scenario:** a local release build contains `ENGINESDIR` and `MODULESDIR` as
  `<checkout>/target/release/build/openssl-sys-<hash>/out/openssl-build/install/lib/{engines-3,ossl-modules}`; the
  hosted build has the same under `/home/runner/work/PdMount/PdMount/target/…`. OpenSSL would `dlopen` a provider or
  engine from there if something asked for one by name. Nothing does: the bundled SQLCipher calls no
  `OSSL_PROVIDER_*` or `ENGINE_*` function, the configuration file is read from `/usr/local/ssl/openssl.cnf` (root's),
  and `OPENSSL_CONF`, `OPENSSL_MODULES` and `OPENSSL_ENGINES` are the user's own environment.
- **Impact:** none shown. The other embedded paths are panic locations under `/home/runner/.cargo/registry/src/…` and
  the fork's checkout under `/home/runner/.cargo/git/checkouts/…` (about 1,200 strings in the local build; workspace
  files appear as relative `crates/…` paths; the Go library is built with `-trimpath`). They reveal the runner's layout
  only, as the threat model's "Local archive check" expects.
- **Fix:** optional. `RUSTFLAGS=--remap-path-prefix=…` for the dist build would shorten the Rust paths; the OpenSSL
  directories would need `no-dso`/`no-engine` features that `openssl-sys` does not pass through, so record them in the
  threat model instead ("only `/home/runner` paths, including OpenSSL's unused engine and module directories").
- **Confidence:** high for the strings (read from an existing local build); medium for "nothing asks for a provider"
  (SQLCipher's source searched, OpenSSL's own lazy loading not traced).

### C1-9: Small inaccuracies and hardening points

- **Rating:** Info
- **Location and content:**
  1. `scripts/build-doctor.sh:6`, `:157`, `:167-183`: says the build downloads Go modules and fails on `GOPROXY=off`.
     `gopenpgp-sys` 0.3.9 ships `go/vendor/` with `go 1.23.0` in `go.mod`, so Go builds in vendor mode without a
     download (the threat model's line 141 is right, the script is out of date). A `GOFLAGS=-mod=mod` in the
     environment would turn downloads back on; `build.rs:137-161` sets `-mod=vendor` only under `DOCS_RS`.
  2. `scripts/build-doctor.sh:159-162`: `git ls-remote --heads "$fork"` takes the URL from `Cargo.toml` without `--`.
     A value starting with `-` would be read as an option. Only relevant for a checkout from an untrusted source, which
     the user is about to build anyway. Fix: `git ls-remote --heads -- "$fork"`.
  3. `about.hbs:103`: `href="{{crate.repository}}"`. Handlebars escapes HTML here and in `{{text}}` (`:106`), and
     crates.io admits only `http`/`https` repository URLs, so the checked-in file is clean (see "Checked and fine").
     A git or path dependency is not checked by crates.io: its `repository` could be a `javascript:` URL. Today the
     only one is the project's own fork. Fix, if wanted: emit the link only when the value starts with `https://`.
  4. `docs/security/threat-model.md:134-135`: "Pull requests run `dist plan` only … nothing is built". True for the
     workflow as committed. A pull request from a fork runs the workflow file and `dist-workspace.toml` of its own
     merge commit, so it can run anything in its own run; what keeps it from a release is the read-only token for fork
     pull requests and the `publishing` condition (`release.yml:55`, `:226`), not `pr-run-mode`.
  5. The fork carries upstream's `.github/workflows/ci.yml` (on every pull request, actions by tag, a shared Rust
     cache) and `release.yml` (manual, `contents: write`, publishes crates). `AGENTS.md` says the fork runs no Actions;
     that is a repository setting and worth confirming, since the files are there.
- **Confidence:** high for 1–4 (file content); 5 is a pointer to a setting.

## Threat model: what is missing

For the verifier to turn into additions; the section "Build-time supply chain" lists inputs but has no actors, assets
or ratings for them.

- **Assets.** A6: the published Releases (archive and checksum of every version) and their binding to a commit. A7: the
  repository's contents and refs (`master`, tags, workflow files). A8: the push credentials on the development machine
  and the developer's files there, which `scripts/ci.sh`, `build-doctor.sh` and the scenario scripts touch.
- **Actors.**
  - S1, a contributor without write access (pull request from a fork): runs their own code in `ci.yml` and in the
    `plan` job of `release.yml`, with a read-only token and no secrets. Controls: no `pull_request_target`, no cache
    shared with tag builds (neither workflow uses `actions/cache`; `setup-go` has `cache: false`), approval for
    first-time contributors (setting).
  - S2, a compromised build input: runner image and apt packages, an action, the dist installer, a crate's build script
    or proc-macro, the Go toolchain, the fork repository. Reaches the archive, and through the token the repository
    (C1-1, C1-2, C1-4).
  - S3, a holder of push rights: the maintainer's account, the push key, a mistaken tag (C1-3). State which tags start
    a release (the real pattern), that the release does not wait for CI, and that the tagged commit need not be on
    `master`.
  - S4, someone between the Release and the user: a replaced asset, a mirror (C1-5).
- **Ratings.** The scale speaks of A1–A5 only. Proposal: publication of an altered archive, or a change to a published
  one, without the maintainer's credentials: High; the same needing a compromised build input: Medium; hardening: Low.
- **Sentences to correct:** lines 129-135 (pinning is possible, C1-2; what stops a pull request, C1-9 item 4), 138
  (toolchain pin is CI only, C1-4), 140 (`--locked`, C1-4), 145 (`v*`, C1-3), 148-149 (add OpenSSL's directories, C1-8).
- **Settings to record as controls, with their checked state:** tag and branch rulesets, immutable releases, default
  token permission, fork pull request approval, Actions off on the fork.

## Checked and fine

- **Triggers.** No `pull_request_target`, `workflow_run` or `issue_comment` in either workflow. `ci.yml` builds pull
  request code with `contents: read`, `persist-credentials: false`, no secrets and no expression inside a `run:` script
  (`ci.yml:16-17`, `:38-59`). In `release.yml` the build, host and announce jobs need `publishing == 'true'`, which is
  false for every pull request (`:55`, `:96`, `:226`, `:293`).
- **Secrets.** Only `GITHUB_TOKEN`; no other secret is referenced in either workflow.
- **Pinning outside the generated file.** `ci.yml:38`, `:45`, `:67`, `:74` and `build-setup.yml:4` use full commits;
  the Rust toolchain and cargo-about versions are fixed in `ci.yml:26-29`, and cargo-about is installed with `--locked`.
- **Caches.** None: no `actions/cache`, no Rust cache, `setup-go` with `cache: false` in all three places. The `dist`
  binary passes from `plan` to `host` as an artifact of the same run, which another run cannot write.
- **Announcement text.** Title and body reach the shell through environment variables and a notes file
  (`release.yml:275-284`), not through expansion in the script.
- **The git dependency.** Both patched crates point at the fork by the full 40-character commit `70f10ff…` in
  `Cargo.toml:81-82` and `Cargo.lock`, equal to the fork's `pdmount-0.5`. A re-registered repository name or another
  fork in the network cannot change what that commit contains. Every other package has a crates.io checksum.
- **Build-time code.** The fork's two `build.rs` only run `prost_build` on `.proto` files in the crate (no include
  outside it except protoc's own well-known types, no network). `gopenpgp-sys` runs `go build -trimpath` on vendored
  modules. `openssl-src`, `libsqlite3-sys` and `aws-lc-sys` build vendored C sources. No build script of the locked
  crates on disk runs `curl`, `wget` or an HTTP client; the one `Command::new("git")` is in `wasm-bindgen-shared`,
  which is not built for the target. Five locked crates had no source on disk and were not read.
- **Licence file.** `THIRD-PARTY-LICENSES.html` at `9818aa1`: only the template's own tags occur (`a`, `li`, `ul`,
  `pre`, `h1`–`h4`, `b`, `p`, head elements); no `script`, `img`, `iframe`, `svg`, event handler or `javascript:`;
  all 490 links are `https://`, one `http://`, or `#` anchors; angle brackets in licence texts are escaped (`&lt;`).
  `ci.yml:53-57` fails when the file differs from a fresh generation.
- **Archive contents.** `dist-workspace.toml:11-21`: no installer script, no source tarball; the archive holds the
  binary, `LICENSE`, `README.md`, `docs/user-guide.md` and `THIRD-PARTY-LICENSES.html`. No file with local data is
  included.
