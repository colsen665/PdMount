### C4-1: The stale-mount rule is per profile, mounts are not: a service start detaches another profile's live mount at the shared default mountpoint
- **Rating**: Medium
- **Location**: `crates/pdmount/src/daemon/launch.rs:185-196` (`stale_action`: "stale" = a `fuse.pdmount` mount while *this profile's* daemon neither answers nor runs), `:213-240` (`detach_if_stale`: `fusermount3 -uz`); `crates/pdmount/src/mounts.rs:16-17` (`is_pdmount` looks at the type only); `crates/pdmount-fuse/src/mount.rs:137-138` (every profile mounts with `fsname=pdmount,subtype=pdmount`, so a mount does not say whose it is); `crates/pdmount/src/daemon/run.rs:51-55` (`--clear-stale` runs before `preflight`); `crates/pdmount/src/service.rs:410-422` (`ExecStopPost=… unmount --if-stale`, run after every stop and failed start of the unit), `:746-748` (`hand_started_daemon` looks at this profile only); `crates/pdmount-core/src/config.rs:417` (every profile defaults to `~/ProtonDrive`); `launch.rs:155-161` (`preflight` calls such a mount stale and advises `unmount --force`, which detaches it too).
- **Actor**: T5 (the user's own configuration; no attacker), with A4 as the asset.
- **Scenario**: Profile `default` is mounted at `~/ProtonDrive` (autostart, a service or by hand). The user adds a second profile for another Proton account, signs it in and runs `pdmount --profile work service install` without setting a mountpoint, so it also uses `~/ProtonDrive`. Install sees no daemon of `work` and starts the unit. The unit's `--clear-stale` finds a `fuse.pdmount` mount at the mountpoint, no `work` daemon answering or running, and lazily detaches `default`'s live mount. `preflight` then passes and `work` mounts the other account at the same path. `default`'s daemon sees an external unmount and stops without a flush (D075), or, if files under the old mount are still open, keeps running and finds `work`'s mount in the mount table, so a later `pdmount unmount` for `default` unmounts `work`'s mount instead. From then on, every tool that writes by path (a sync job, an editor's save, `rsync` or `git` in the mount) writes into the other account, with no message. On systemd the same detach also runs from `ExecStopPost=` whenever `work`'s unit stops or fails, and at boot or login whichever service starts second takes the path. Before M5 the second start failed in `preflight`, but its advice (`unmount --force`) led to the same detach by hand.
- **Impact**: User data goes to the wrong Proton account (confidentiality between accounts, e.g. private files uploaded into a work account), and the other profile's mount ends without a flush. It comes from a default configuration, not from untrusted input, so it is not rated High.
- **Fix**: Make the stale rule tell profiles apart: mount with `fsname=pdmount:<profile>` (the source field of `/proc/self/mountinfo`) and treat a mount as this profile's only when its source matches, leaving every other `fuse.pdmount` mount alone. Mounts from older versions have the plain `pdmount` source, so also check that no profile's daemon names this mountpoint in its pid file (second line, `$XDG_RUNTIME_DIR/pdmount/*.pid`) before detaching it. Separately, refuse `mount` and `service install` when another profile's pid file names the same mountpoint, and change `preflight`'s message to name that profile. Add a unit test with two profiles' paths in `launch.rs`.
- **Confidence**: high for the code path (traced); the prevalence depends on how users set up a second profile.

### C4-2: Unicast `PrepareForShutdown` signals from another local user stall the logind task: the shutdown flush does not start and the delay lock is not released
- **Rating**: Low
- **Location**: `crates/pdmount/src/logind.rs:129-139` (a message whose sender is not logind's current owner makes a `GetNameOwner` call, awaited inside the `select!` arm, with a 10 s limit), `:189-198` (the match rule names the well-known sender `org.freedesktop.login1`). zbus 5.19.0 `src/match_rule/mod.rs:219-228` (`matches` ignores a well-known sender: "We can't match against a well-known name"); `src/connection/socket_reader.rs:77-108` (the socket reader awaits `broadcast_direct` into a stream's queue, so a full queue stops it from reading anything else, method replies included); `src/connection/mod.rs:47`, `:994-996` (64 messages per stream, no overflow).
- **Actor**: T1 (any local user on the system bus).
- **Attack**: dbus's default system policy allows any connection to send signals (`<allow send_type="signal"/>`), including unicast signals addressed to one unique name, and the bus delivers those whatever the recipient's match rules say. The daemon's unique name can be found with `ListNames` and `GetConnectionUnixUser`. The attacker sends a few thousand unicast signals with path `/org/freedesktop/login1`, interface `org.freedesktop.login1.Manager` and member `PrepareForShutdown`. zbus does not filter them by sender, so each one reaches the stream. For each, `run` calls `GetNameOwner`. Once 64 forged signals are queued, the socket reader blocks on the full queue and cannot read the `GetNameOwner` reply, which sits behind more forged signals, so each call times out after 10 s. The loop then handles one forged signal per 10 s. A real `PrepareForShutdown(true)` waits behind the queue, so the flush at shutdown does not start. The `Release` command waits in the same loop, so the delay lock holds the shutdown for logind's full `InhibitDelayMaxSec`. Each queued message may also carry up to 16 descriptors (the system bus's `max_message_unix_fds`), which stay open in the daemon while the message waits (about 1000 at most).
- **Impact**: The flush starts only at SIGTERM. OpenRC kills user services about 16 s later at shutdown (M5.0), so changes made just before a shutdown stay on this machine until the next mount (no loss, D075/D095). The shutdown waits up to `InhibitDelayMaxSec`, which another user could also cause with an inhibitor lock of their own. The sender check itself holds: a forged signal never starts or cancels a flush.
- **Fix**: Drop signals that carry a destination (`message.header().destination().is_some()`), because logind broadcasts `PrepareForShutdown` and the bus already filters broadcast signals by the resolved sender of the match rule. Do not make a bus call for each mismatched message: follow `NameOwnerChanged` for `org.freedesktop.login1` (sender `org.freedesktop.DBus`, which no client can claim), or ask `GetNameOwner` again at most once every few seconds. Run the call outside the `select!` arm so that `Release`/`Take` go on. Add the unicast case to the threat model's zbus paragraph.
- **Confidence**: high for the zbus behaviour (read in the source) and the policy; the attack was not run.

### C4-3: A pending marker whose `time` is beyond `i64::MAX` panics the marker reader of its tree
- **Rating**: Low
- **Location**: `crates/pdmount-core/src/engine/marker.rs:105-112` (`age`: `UNIX_EPOCH + Duration::from_secs(self.time)`; std's `SystemTime + Duration` panics on overflow), `:141-157` (`parse` takes any `u64` for `time`), `:640` (`replace_seen` calls `is_stale` for each new marker revision, in the `run_markers` task); the same call in `crates/pdmount/src/incoming.rs:62-63` (`status`). `status::local_time` handles the value (`i64::try_from`).
- **Actor**: T2: another device of the account in My Files, or an owner or editor of a share for a share's tree (area 1, C1-3).
- **Attack**: Upload `.pdmount/<any uuid>.pending` as `{"version":1,"time":18446744073709551615,"entries":1,"bytes":1}` (39 bytes, so it passes the size, block and version checks). At the next pass the engine's `run_markers` task panics in `replace_seen` and ends (panic = unwind, the task's `JoinHandle` holds the panic, and nothing restarts it, cf. C5-5). The announced revision is never stored, so the same happens after every restart while the file exists.
- **Impact**: For that tree, no other device's marker is read, shown in `status` or announced again for the daemon's lifetime: other devices' warnings of pending changes are silenced from remote input. The daemon and the mount go on. This is a remote-triggered panic, which C5-5 did not find.
- **Fix**: In `parse`, refuse a `time` above `i64::MAX` or more than a day ahead (`MarkerError::Invalid`), and use `UNIX_EPOCH.checked_add(...)` in `age` (a marker whose time cannot be represented counts as age zero, not stale). Add a test with `u64::MAX`.
- **Confidence**: high (std's `Add` implementation panics; the call order was traced).

### C4-4: Stop signals between the FUSE mount and the signal handlers kill the daemon outright
- **Rating**: Low
- **Location**: `crates/pdmount/src/daemon/run.rs:168` (mounted), `:195-199` (background work and uploads start), `:204-255` (auth, conflict and marker tasks, the pid file, the control socket, `restore_late_attach` with its bus connection of up to 2 s), `:277` (`StopSignals::new()`, the first handler for SIGTERM/SIGINT/SIGHUP); `daemon/stop.rs:5-7` says the signals are listened to "from before the mount is ready", which holds for readiness but not for the mount.
- **Actor**: none (robustness of the stop path, A4 availability): a `systemctl --user stop`, a logout or a shutdown while the unit is still activating, or Ctrl-C on `mount --foreground`.
- **Scenario**: A signal in this window has its default action and kills the process at once. The mount is left stale (systemd's `ExecStopPost=` or the next `--clear-stale` clears it), uploads already started are cut off, nothing is flushed or committed beyond SQLite's own commits, and no tokens are saved. It is the same as a crash, which the journal survives (DESIGN §17's accepted crash risks apply), but the stop path's guarantees (D075, D092) do not hold here.
- **Fix**: Create `StopSignals` at the top of `run_foreground`, before `--clear-stale`. Race the start against it: a signal before the mount exits 0 (or 78 under `--service`) without mounting, and a signal after the mount goes to the normal stop (`wait_for_stop` sees it as already pending). Keep the store and token logic as it is.
- **Confidence**: high for the order; the window is short (usually well under a second, longer with a saved attach whose bus is slow).

### C4-5: Minor hardening (Info)
- `service.rs:193-195`, `:252-264`, `:322-330`: `command` and `output_log`/`error_log` are written with `eval_quote`. `supervise-daemon.sh` expands them unquoted on its `eval` line, so they are split at spaces before `eval` joins them with one space: a binary or state path with two spaces in a row becomes another path (the start fails, or the log goes to a sibling directory in the user's own tree). `eval_word`'s comment describes this for `command_args`. Use `eval_word` for these too, or refuse runs of white space.
- `service.rs:259`, `:264`, `:274-281`: `profile=${RC_SVCNAME#pdmount.}` goes into `command_args`, which `supervise-daemon.sh` evaluates. `start_pre` accepts any `pdmount.?*` link name, so a link name containing `$(…)` would run in the service's shell. Only the user can create links in `$XDG_CONFIG_HOME/rc/init.d`, so this is same-uid. Cheap to close: have `start_pre` refuse names outside `[a-z0-9][a-z0-9_-]*`, which is the rule for profile names.
- `supervise.rs:180-209`, `run.rs:168-278`: the readiness pipe (descriptor 3 under OpenRC) is not close-on-exec, so every child spawned before readiness inherits its write end: `fusermount3` (fuser's mount), the keyring helper and `notify-send` from `resume::announce` (`desktop_sent`, up to 10 s). If the start then fails, `supervise-daemon --start` waits until those children exit before it sees the failure. The descriptor is also closed later by number. Take ownership at startup instead: open `/proc/self/fd/<n>` into a `File` (close-on-exec), close the original at once, and keep the `File` until readiness. (Checked: opening an anonymous pipe through `/proc` does not block without a reader, unlike a named FIFO, and the write then gets `EPIPE` with SIGPIPE ignored, so the readiness write cannot hang.)
- `marker.rs:610-619`, `:789-811`: an adopted link (any file named `<this device id>.pending` in `.pdmount`) is trashed later without checking that it is still named so and still in the marker folder. In a share, a member who moves or renames another file there gets it trashed under this user's account. The attacker can trash it themselves, so this only changes who the share's history names. Check the node's name and parent in `trash_own_marker`.
- `marker.rs:176-189`: `is_hidden` misses some invisible characters: tag characters U+E0000–U+E007F, variation selectors U+FE00–U+FE0F, U+034F, Hangul fillers U+115F/U+1160/U+3164/U+FFA0, and U+180B–U+180D. These only allow display spoofing in `status` and notifications. Control characters, C1 (CSI) and bidirectional overrides are already caught, so no terminal escapes get through. Area 1 suggests reusing this set elsewhere, so widening it helps there too.
- `service.rs:760-761`, `:831-832`: the unit files are written 0644 on purpose and name the binary, the secret-storage flag, the mountpoint and the log path (R-5's remark, now for two more files). `current_binary` does not check that the binary and its directory are not writable by other users. A unit that runs a binary from a shared or temporary directory at every login would run another user's code (Critical if it happened, but it needs that installation). Warn when the binary or a parent directory is group- or world-writable, or is under `target/` or a temporary directory.
- `daemon/stop.rs` / `run.rs:302-315`: after the second signal, further signals are taken by tokio's handler and ignored. Every wait after that is bounded (0.3 s for the session, no wait for steps, the commit), except the final token save, whose keyring call is bounded only by the keyring timeouts of area 3. A third Ctrl-C therefore does not end a foreground daemon at once. This is the documented behaviour; the log line could say "send SIGKILL to stop at once".

## Checked and fine (area C4)
- systemd quoting (`service.rs:217-224`, `:383-445`): `%` and `$` are doubled. Anything outside a safe set is put in double quotes with `\` and `"` escaped, which together cover systemd's C escapes and `;` words. Control characters are refused for the binary, mountpoint and log (`plain`). The binary is absolute (no `-`/`@`/`+`/`!` prefix meaning). `%i` (not `%I`) with validated profile names. The test build's `Environment=PDMOUNT_MOUNT_ARGS` refuses quotes and backslashes in the path. No `/etc` file is written; the elogind drop-in is only printed, and `doctor` only reads elogind's and `user@.service`'s files.
- OpenRC files: `conf.d` holds only fixed flags, numbers and the two quoted log paths. `pdmount_mount_args` uses `eval_word`, so `$`, quotes and backticks in a path stay literal through the assignment and the `eval`. The D109 `start()` reads only the user's own pid file in `$XDG_RUNTIME_DIR`, and with a stale pid (`kill -0` fails) it stops only the supervisor of the failed start. Files are written through a `create_new` temporary file and `rename` (no symlink is followed). The log is created 0600 in a 0700 directory before `supervise-daemon` opens it. `rc-update`, `rc-service` and `systemctl` run without a shell.
- Supervisor options: `--notify-fd` needs `--foreground`, n ≥ 3 (clap range plus a check), and is written only when it is a FIFO. `NOTIFY_SOCKET` must be absolute or `@abstract`, is sent with a 2 s timeout, and is removed from a background launch's daemon. systemd's default `NotifyAccess=main` ignores children. Exit 78 is used only before `REPORTED_READY` (set before the report is sent), also for a command line that does not parse under `--service`; after readiness every failure exits 1.
- `--clear-stale` and `--if-stale` within a profile: a control socket that errors counts as answering, the pid file is checked against `/proc/<pid>/cmdline`, only `fuse.pdmount` mounts are touched, and `fusermount3` gets the path as one argv element after its flag (mountpoints are made absolute). See C4-1 for the cross-profile case.
- Process arguments: the daemon's argv holds the profile, `-v`, the secret-storage flag, `mount` options and the mountpoint, with no secret. `fusermount3` gets the flag and the mountpoint. `notify-send` gets `--app-name=PdMount -- <summary> <body>`, so a name starting with `-` is no option, and the attached bus goes through the environment. Shutdown and resume notifications carry only counts and the grace; a marker notification's body has only numbers and its summary the cleaned device name. `attach_hint` only prints `sh`-quoted lines. Nothing runs through a shell.
- logind: the sender check against `GetNameOwner` holds, because the system bus sets the sender field and broadcast forgeries are filtered by the bus through the match rule. Only `PrepareForShutdown`'s boolean is read. The lock descriptor is duplicated close-on-exec and released at the flush's end, at a second signal, after `Prepare(false)` or `NoLogind`, and when the `Inhibitor` is dropped. `pdmount fake logind` and `logind_stub.rs` are behind `fake-backend`.
- Flush and stop: one grace from the first trigger (`since`); a second signal aborts the flush, releases the lock and sets `hurried`; `hurry_on_signal` covers signals during the stop; `syncfs` runs on a plain thread with a 5 s limit; the pid file is written in the 0700 runtime directory and removed last; `unmount` and an external unmount do not flush, as designed.
- Pending marker, writing: the JSON has `version`, `device` (left out in shares), `time`, `entries` and `bytes`, and no paths. It is mode 0444 and goes through the backend, not the journal, bounded by the deadline. The folder is checked to be the root's child and not trashed before reuse. The link in `meta.pending_marker` or a listing makes sure that a marker whose commit was lost is still trashed at the next drain.
- Pending marker, reading: the listing size must be at most 4 KiB, there must be one block, the fetch goes into a 4 KiB buffer (a longer block is refused), `version` must be 1 with typed fields, only canonical `<uuid>.pending` names count, and the device's own marker is skipped. Device names are cleaned before the log, `status` and notifications. serde_json's error text does not echo the input. `notified` is pruned to the current markers. Volume and spam in shares: C1-3.
- `.pdmount` is read-only in the mount: creating, removing or renaming the name in the root, any write path inside it, `setattr` and `access(W_OK)` get EROFS, and the shown attributes lose their write bits (`engine/access.rs:66-99`, `:103-118`).
- `resume.rs`: counts only; the follow-up notification is sent only after a `notify-send` that exited 0 within 10 s (killed after that); the watch stops with the daemon.
