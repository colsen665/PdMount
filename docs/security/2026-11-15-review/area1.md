Actor for every finding below unless said otherwise: T2, another Proton user who owns, or can edit, a share the user accepted. That actor writes the share's names, its content (any file in it, `/.pdignore` and `/.pdmount/` included), its creator address, and can revoke or trash the share's root at any time.

### C1-1: A share's local-only files are deleted with the share's state when it goes, and any member with write access decides what is local-only

- **Rating**: High
- **Location**:
  - `crates/pdmount/src/roots/shared.rs:749-773` (`SharedRoot::remove`): `queued = counts.pending + counts.parked`; with 0 queued, or after an export that reports no error, `purge_tree`/`retire_tree` delete `trees/<key>/`, staging included (`roots.rs:987-1004`, `:1172-1190`).
  - `crates/pdmount-core/src/engine/orphan.rs:106-150` (`export_queued`): iterates `self.journal.inos()` only.
  - `crates/pdmount-core/src/journal.rs:1369-1374` (`plan`: a local-only node, or one in a local-only folder, is `Plan::Done`) and `:687-698` (`done` removes the entry): a local-only file never stays in the journal, so it is neither counted nor exported.
  - `crates/pdmount-core/src/engine/ignore.rs:90-111` (`keep_ignore_rules`: the rules are the tree root's `/.pdignore`, downloaded from the drive, plus the profile's local file) and `crates/pdmount/src/roots.rs:1044` (`local_ignore` of My Files given to every further tree); `engine/namespace.rs:156`, `:188`, `:264` (create, mkdir and rename take the flag from these rules).
- **Attack**: The owner (or any editor) of a share writes `/.pdignore` with the line `*` (or `**`) at the share's root. In every member's PdMount the share is a tree whose root is that folder, so its `/.pdignore` becomes that tree's rule file (§7.7: "synced like any file"). From then on every file and folder the member creates or renames into the share (an editor, a `git` checkout, `rsync`'s temp-then-rename) is local-only: it shows in the mount like any file, is never queued and never uploaded, and `status`, `queue` and the `unmount` drain all report nothing pending. When the owner later revokes the share, or trashes its root for a moment (the first "not found" removes the share, `shared.rs:788-805`), `remove` counts 0 queued changes and deletes `trees/<key>/`. Local-only content lives only in that staging (DESIGN §7.7, §8 "there is no other copy"), so the user's files are gone without an export, a notification or a log line about them. If other changes were queued, they are exported, but the local-only files still are not (`incomplete()` counts only entries with an error), and the state is purged as well.
  The same loss happens without malice: files matched by the user's own `~/.config/pdmount/<profile>.pdignore` (`*.tmp`, `node_modules/`, a build folder) inside a share are deleted at the share's revocation by its owner, which contradicts D114's "nothing staged is deleted (RQ3)".
- **Impact**: Loss of the user's data written into the mount, triggered by another user (High: "silent … loss of A4 triggered by untrusted input"). With the `.pdignore` step, the other user also silently stops the member's uploads to the share for as long as the rule stays (integrity of what the member believes is shared).
- **Fix**: (1) At a share's removal, treat every staged inode as content to keep: export the staging of local-only nodes too (iterate the staging directory's inodes, not only the journal), count them in `queued`, and call `purge_tree` only when no staging file remains unexported (else `retire_tree` with `keep`). (2) Do not take the rules of a tree's remote `/.pdignore` on another user's volume (`!spec.own`); keep only the profile's local file there, or require an opt-in per root. (3) Show local-only entries per tree in `status` (a count), so a tree with content that never uploads is visible. Add a scenario: a share with a `.pdignore` and a new file, revoked; the file must be under `orphaned/`.
- **Confidence**: high (traced: rule source, create/rename flagging, planner, journal removal, count, export loop, purge). Not run.

### C1-2: A new share can take over the folder name of an existing share, so writes by path go into the other user's share

- **Rating**: Medium
- **Location**: `crates/pdmount/src/roots/shared.rs:109-152` (`display_names`): names that do not clash are put into `taken` first; only then do the clashing names get `<name> (<owner>)`, moving to `(<owner>, n)` when that form is taken. `:507-513` (`refresh`: a changed display name is applied in place, `TreeSet::rename`); `crates/pdmount-fuse/src/trees.rs:226-239`.
- **Attack**: Alice and Bob each share a folder `Team` with the user; the Shared mount shows `Team (alice@…)` and `Team (bob@…)` (D107), and the user's scripts, editor projects or an `rsync` job use `~/Shared/Team (alice@…)/`. Mallory, whose share the user accepted earlier for something else, renames her shared folder to `Team (alice@…)` (the creator address is visible to her as a member of Alice's share, or simply guessed). At the next `DriveShareRefresh` her name does not clash, so it is taken first; Alice's share then gets `Team (alice@…, 2)` and is renamed in place, and Mallory's tree now answers at `Team (alice@…)`. Everything the user's tools write by that path goes into Mallory's volume (she gave the user the editor role on her own share). A variant without a pre-existing clash: Mallory shares two folders named `Team` and `Team (alice@…)`; Alice's plain `Team` disappears and the folder that reads as Alice's is Mallory's. The owner suffix, the only attribution the mount shows, is under the other user's control, and `status` shows the same name.
- **Impact**: The user's data reaches another user's volume, chosen by that user, with no signal (A4 confidentiality: "nothing uploaded that the user did not write there" holds by path, not by intent). Needs an accepted share from the attacker; no data loss.
- **Fix**: Make shown names sticky: a share keeps the name it is shown under for as long as it stays in the listing (or the mount), and a new or renamed share must avoid every name in use (it gets the suffix, never the incumbent). Treat a share name that ends in ` (<text>)` where `<text>` matches another share's owner label, or the suffix pattern in general, as clashing so it is always suffixed with its own owner. Log and notify when an existing share's shown name changes, since paths through it change.
- **Confidence**: high for the naming (traced with the code's order of `taken`); the impact assumes tools that write by path.

### C1-3: Pending markers planted in any share: unbounded fetches and one `notify-send` per marker

- **Rating**: Medium
- **Location**: `crates/pdmount-core/src/engine/marker.rs:8` (reading is on in every tree), `:549-603` (`scan_markers`: every `.pdmount/<uuid>.pending` in the tree root is fetched, no count limit), `:655-666` (`replace_seen`: every new or changed marker is announced); `crates/pdmount/src/roots.rs:1560-1561` (`announce_tree` subscribes every further tree, viewer shares included); `crates/pdmount/src/incoming.rs:12-23` (`announce`: `notify::desktop` per marker, no `Coalescer`); `crates/pdmount/src/notify.rs:107-137` (each call spawns a thread and a `notify-send` child).
- **Attack**: The owner or an editor of a share uploads N small files `/.pdmount/<random uuid>.pending` with valid JSON (`time` = now, a device name of their choice such as "Proton Support: re-login required"). Each member's PdMount fetches all N (one gate turn and two API calls each) after the next event pass, then calls `notify::desktop` N times in one go: N threads and N `notify-send` processes at once, and N notifications whose summary carries the attacker's 64-character device name. Rewriting the markers (new revisions) repeats it at every scan (after each event pass; every 30 s while the share is the volume in use, else every 10 min, and at least every 120 s via `SCAN_FALLBACK`). `status` prints one `Incoming:` line per marker. D114 states that a member's marker reaches only the member's own devices, but the reading side does not filter by owner or device: every member running PdMount reads every member's markers.
- **Impact**: Remote-triggered resource use in the user's session: process and thread bursts (with a large N, `RLIMIT_NPROC` for the whole uid), API budget of the shared session (429s hit My Files too), notification spam with attacker text (phishing-like, T4 notes notifications as a user channel). Medium: DoS from remote input.
- **Fix**: Cap markers read per tree and pass (e.g. 16; log the rest); coalesce incoming notifications per tree (`notify::Coalescer`, one per 30 s, "N devices have changes on their way"); in trees on other users' volumes either do not read markers at all, or announce only device ids the user's own devices are known to use (a list kept in My Files' store); update DESIGN §14.5 and D114's wording and the threat model's marker line (count bound).
- **Confidence**: high for the code path; the process burst size was not measured.

### C1-4: In a share, folders are created and blocks requested with the default address instead of the share's membership address

- **Rating**: Low
- **Location**: `sdk/crates/proton-drive-sdk/src/node/folder.rs:31-49`, `:110-113` (`FolderOperations::create`: signing key, passphrase, name and hash-key signatures and `SignatureEmail` from `get_default_address`; reached from `crates/pdmount-backend/src/proton.rs:1213-1228` `create_folder`); `sdk/crates/proton-drive-sdk/src/block/upload.rs:108`, `:198` (`BlockUploadPreparationRequest.address_id` = default address, while the blocks and manifest are signed with the membership address's key, `sdk/crates/proton-drive-sdk/src/node/revision.rs:783`, `:926`); `sdk/crates/proton-drive-sdk/src/node/draft.rs:148-158` (any failure of the membership lookup silently falls back to the default address). The official SDK takes all of these from the context share's member address: `cs/client/js/src/internal/nodes/nodesAccess.ts:460-487` (`getNodeSigningKeys` → `getContextShareMemberEmailKey`), `cs/client/js/src/internal/nodes/nodesManagement.ts:349`, `cs/client/js/src/internal/upload/streamUploader.ts:366`, `:548`.
- **Scenario**: A user with several addresses accepted a share on an alias (the invitation was to the alias). `mkdir` in the share's tree (and every folder an `rsync`/`git` copy creates) signs the folder's metadata with the user's default address and names it as `SignatureEmail`; every member and the owner see the default address as the folder's author. Each upload sends the default address's id with the block requests. A transient error in the membership lookup makes a whole upload signed by the default address (logged by the SDK at warn level only). The real-account X9 run passed, but on a test account whose membership address is probably its default; whether the server refuses a mismatch was not verified.
- **Impact**: Disclosure of the user's primary address to the members of a share joined under another address (personal data, not an asset of the threat model as written); signatures inconsistent with the official clients (possible "unverified author" or refusals with multi-address accounts). No integrity loss of content: the SDK signs blocks and manifest with the membership key.
- **Fix**: In the fork: `FolderOperations::create` and the block-upload requests take the membership address of the parent (`NodeOperations::get_membership_address`, as `move_single`/`rename` already do, `sdk/crates/proton-drive-sdk/src/node/operations.rs:224`, `:606`); fail the draft instead of falling back to the default address when the parent is not in the user's own volume. Record the patch in `docs/sdk-patches.md`; add to the open X9 check: create a folder on an account whose invitation went to a non-default address and read its `SignatureEmail` from the owner's side.
- **Confidence**: high for the code (fork and official SDK read); the server's behaviour with a mismatch not verified.

### C1-5: Share names and owners are cleaned of control characters only, and reach the log unescaped through the orphan path

- **Rating**: Low
- **Location**: `crates/pdmount/src/status.rs:100-104` (`printable`: `char::is_control` only); `crates/pdmount/src/roots/shared.rs:68-83` (`owner_label`: control characters and `/` only), `:62-64` (`usable`: a newline or escape in a share name is accepted); `crates/pdmount/src/roots.rs:1142`, `:1148`, `:1158` (`dir = %dir.display()`: Display formatting, so tracing-subscriber 0.3.23 escapes nothing in that field, not even ESC; only the `message` field is sanitized); `notify_held` and the orphan notification (`shared.rs:831-838`, `roots.rs:1163-1166`) put the raw name in the summary.
- **Scenario**: A share named `Report\u{202E}fdp.exe` or with an owner address carrying U+2066–U+2069 or U+200B reorders or hides text in `status`, the owner suffix and notifications; device names already strip these (`marker.rs:161-186`, `is_hidden`), share names and owners do not. A share named `x\nERROR … the daemon …` that is revoked with changes queued writes the name with a raw newline (and escape sequences) into the daemon log through the `dir` field, forging log lines (T2's "log injection").
- **Impact**: Display spoofing and log injection; no file system effect (the names stay inside `orphaned/`, cut to 200 bytes).
- **Fix**: Use `marker::clean_device_name`'s `is_hidden` set in `printable` and `owner_label`; log the orphan directory as `dir = ?dir` (Debug escapes) or log only the tree key; keep the mount's own names as they are.
- **Confidence**: high.

### C1-6: A refused event stream with an undecryptable root removes the share, against D119

- **Rating**: Low
- **Location**: `crates/pdmount-backend/src/shared.rs:426-433` (`ShareTree::poll_events` checks the root with `get_nodes`, which maps `NodeLookup::Degraded` to `None`, `crates/pdmount-backend/src/lib.rs:98-105`, and then calls `gone_now`).
- **Scenario**: Every other "is the root gone" path uses `get_nodes_checked` and keeps a degraded root (D119). Here, when the owner's volume stream answers not found or permission denied while the root's metadata cannot be decrypted (a key rotation, a root the owner corrupted), the share is reported gone: it leaves the mount, its queued changes are exported and its state deleted (with C1-1's loss for local-only files), and it is not opened again while the listing has it (`inner.gone`).
- **Impact**: Unwanted removal; data kept for queued changes. Whether the server can refuse the stream while still returning the root was not traced.
- **Fix**: Use `get_nodes_checked` and call `gone_now` only for `NodeLookup::Absent`.
- **Confidence**: high for the code, low for reachability.

### C1-7: Minor (Info)

- Export file modes: `export_file` (`orphan.rs:160-176`) sets the exported file to `mode & 0o777` of the node, which a share's owner may have set (`0666`, `0777`), and `create_dir_all` makes `orphaned/` and its folders with the umask (`0755`), while staging is `0700`/`0600` (`staging.rs:249-251`, `:347`). Plaintext stays private only through the data directory's `0700`. Make the export directory `0700` and files at most `0600 | (mode & 0o100)`.
- Listing work before the cap: `shared_listing` (`proton.rs:1385-1517`) reads up to 64 pages and calls `get_share` once per share id ever seen (cached for the daemon's life in `share_info`, never pruned) and `get_nodes_uncached` for every root, before `select` applies the 32-share cap; these calls do not take the session's background gate, and a `DriveShareRefresh` triggers one full listing per core poll (30 s). Bounded by the shares the user accepted; take a gate turn per page and per batch, and prune `share_info` to the current listing.
- Slot exhaustion: each share that comes back after a removal takes a new slot (`trees.rs:107-115`); 65 534 per mount. An owner who revokes and re-shares up to 32 shares per core poll needs about 17 h to exhaust them, after which no new share mounts until a remount. Log once when 90 % of the slots are used.
- Per-share memory: the 32-share cap bounds RAM pools (32 × 16 MiB), not the in-memory tree: a listed folder holds all its children (`list_children` collects every page), so a share folder with millions of entries costs that much memory when browsed or indexed. Same as My Files, but the content is another user's now.
- A share revoked while the Shared mount is not mounted is never opened again, so its `trees/<key>/` (with any queued changes) stays without an `Orphaned:` line until `reset --orphan-trees`. Consider listing tree directories that no open or listed share uses in `status`.
- In a share, the pending marker (D114) still names the device by its stable UUID in the file name; all members can correlate a member's devices over time. Acceptable per D114; a per-share random id would avoid it.

## Checked and fine (area C1)

- Write gate: every write path checks `ensure_writable` (`engine/access.rs:86-99`): `open` for writing, `write_local` (also for handles opened before the gate closed), `setattr` (any change), `create`, `mkdir`, `unlink`, `rmdir`, `rename` (both ends). `link`, `symlink`, `mknod` are EPERM, `setxattr` ENOTSUP, `fallocate` EOPNOTSUPP (`pdmount-fuse/src/lib.rs`). The virtual top level and the `Shared files` folder answer EROFS to every change (`lib.rs:674`, `:734`, `:758`, `:777`, `:827`, `:913`); a rename between slots is EXDEV (`lib.rs:849`), and between a share and My Files the kernel answers EXDEV (two mounts). Shared single files: gate closed (`may_write` needs a folder) and `ShareTree` refuses every change with `PermissionDenied` (`crates/pdmount-backend/src/shared.rs:354-410`). Viewer role: gate closed at the open and at each listing; a server refusal closes the gate and holds the queue (`rights.rs`), and a refusal while the listing still says Editor does not reopen it (no loop: `apply_role` runs only on a role change). The server enforces roles in any case.
- Role change against a running step: `hold_all` marks every entry and every later one (`state.hold`), parks the idle ones, leaves a step in flight to finish and parks it only if it needs another (`journal.rs:972-994`); release forces only entries held for this reason. Retire: a change acknowledged after `retire` is answered EIO (`after_commit_kept`, FUSE `committed`), so nothing acknowledged escapes the export.
- Router and slots: inode `(slot + 1) << 48 | n`, slots never reused (`trees.rs`), unknown or removed slots answer ENOENT/EIO (`lib.rs:161-185`), `..` of a tree root is the top level only for the root; no path from a share's inode leads into another tree.
- Local paths from remote input: the tree state directory is `blake3(volume ‖ 0 ‖ root)[..32]` hex (`paths.rs:111-119`), never a server string; the orphan directory name is the shown name (already free of `/`, NUL, `.`, `..`), cut to 200 bytes, plus a timestamp, and a fresh name is chosen while one exists (`roots.rs:1108-1124`); paths under `files/` come from tree names that `representable` filters (no `/`, NUL, `.`, `..`, over 255 bytes, `vfs.rs:574-580`) and `relative` drops `.`/`..` again (`orphan.rs:87-96`); export uses `rename` of a fresh staging snapshot (no symlink follow), and the tree has no symlinks (`NodeKind` is File or Folder). Nothing outside the profile's data directory is written. `reset --orphan-trees` moves `trees/<key>/` by hash name. Nothing reads `orphaned/` back except `status` (counts and the manifest's tree name, through `printable`); no code uploads from there.
- Share names: `usable` refuses empty, `.`, `..`, `/`, NUL; over-long names are cut on a character boundary; owner labels lose control characters and `/` and are cut to 64 bytes; the suffixed name stays within 255 bytes (`shared.rs:62-107`; but see C1-2 and C1-5). `status` lines go through `printable`; structured log fields other than `%`-formatted ones are Debug-escaped by tracing-subscriber; `notify-send` gets argv after `--`, names only in the summary (plain text in the protocol).
- Listing: kind from the listing must match the root's kind (`proton.rs:1505`); trashed roots and Photos/Album roots are left out (`share_root`); roles come from the server's `direct_role`, `Inherited` mapped to Viewer; degraded roots are kept, not removed (D119), in `with_degraded`, `ShareTree::get_nodes_checked` and `file_node` (but see C1-6).
- Event stream of another user's volume: a shared file's tree passes only events of its own link (`crates/pdmount-backend/src/shared.rs:435-440`); a folder share's engine only attaches nodes under folders it has listed; the core stream is read at most 16 pages per poll (`poller.rs:345`, `:521`); other volumes poll every 600 s, the one in use every `poll_interval`, with the official back-off (`poller.rs:42-60`). A retired tree is skipped by later passes and its last pass is awaited before the export (`poller.rs:244-251`, `roots/shared.rs:739-747`).
- Content integrity in shares: block reads go through `get_block_map`, which verifies the manifest signature with the keys of the revision's `SignatureEmail` (or the node key) before any block is used (`sdk/crates/proton-drive-sdk/src/node/file/block_map.rs:356-374`, P17), the same as My Files; a share member's content is verified as signed by its author, which is all a share can promise. Uploads sign blocks, manifest and content key with the membership address's key (`sdk/…/node/draft.rs:186-212`, `node/revision.rs:926`); renames and moves use the membership address (`node/operations.rs:224`, `:606`); see C1-4 for folder creation and the block request's address id.
- Revocation cleanup: kept per tree key, a returning share waits for it (20 s) instead of opening a second engine on the store; the stop waits for cleanups within its deadline (`roots.rs:1485-1557`, `roots/shared.rs:617-635`).
- Test-only surfaces: `[[roots]] kind = "test"` is refused without the `fake-backend` feature and a fake drive (`roots.rs:773-776`); `pdmount fake root|share-file|share-role|core-signal|photo` are `#[cfg(feature = "fake-backend")]` in `main.rs`; `computers` is refused by config validation.
