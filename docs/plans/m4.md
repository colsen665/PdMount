# M4 implementation plan: performance and operations

Task specifications for milestone M4 (D056). Status, checkboxes and handoff notes live in `TODO.md`; reasons in
`docs/decisions.md`; the specification in `DESIGN.md`.

## Context

M3 is done (TODO.md, 2026-10-25). The pre-M4 review's fix groups are applied, except the rest of G6, which is optional
(2026-10-27). M4 (DESIGN.md §16) covers:
- SLO instrumentation and benchmarks;
- P7 parallel uploads;
- pins;
- the writeback-cache experiment;
- `cache gc`;
- queue tooling;
- service integration (an XDG autostart entry instead of a systemd unit, D059);
- documentation.

Exit criteria (§16):
- the §5.7 SLOs are met;
- the benchmarks run over the fake backend with an 80 ms RTT / 20 MB/s profile, and:
  - `git status` on a warm git.git takes at most 2× local btrfs;
  - untarring 5k small files takes at most 3× local (time to acknowledgement; 15× since M4.5, D065);
  - cached sequential reads reach at least 500 MB/s;
  - `cache gc` holds the cap ±5 %.

Decisions taken with the user on 2026-10-27:
- **D056:** M4 works like M3 (D039). The plan is in `docs/plans/m4.md`, the work is committed one commit per task as `M4.n: <title>`
  after `scripts/ci.sh` passes, nothing is pushed, and the start is tagged `m4-start`. A session may do **several tasks** where
  the context allows; the "Sessions" table below recommends the batches.
- **Efficiency items (pre-M4 review E1–E19): measure first.** The benchmarks and the fake's network profile come first.
  An Opus triage (M4.5) then picks the E items that the measurements implicate, plus cheap S-sized ones. The rest stay
  Known gaps, with the numbers.
- **One user-gated real-account task (M4.15):** P7 and Q7 (rate limits) are checked on the real account, stopping at the
  first 429 (D030).
- **git.git** for the benchmark is cloned from `https://git.kernel.org/pub/scm/git/git.git` (no GitHub, D023).
- **D059:** `pdmount autostart` writes an XDG autostart entry. It replaces the systemd user unit, because this machine
  has no systemd.

Today's state (code exploration, 2026-10-27):
- **Instrumentation.**
  - `metrics.rs` has 13 plain counters ("Latency histograms follow in M4"), and `pdmount stats` prints them along with the pool slots.
  - Missing: histograms, timing, queue gauges, the Prometheus textfile, slow-request WARN logs and spans.
  - `scripts/bench/{latency,read}.sh` time requests only on the client side.
- **Fake.**
  - `set_latency` is a single per-process constant on read calls only, settable from tests only. A running daemon cannot get latency.
  - There is no bandwidth model.
  - One global `parking_lot::Mutex<State>` covers everything, with flock and journal I/O under it.
  - `child_named`, `list_children` and `used()` scan every node (E19).
- **P7.**
  - P7 is in the fork (`client.rs:384` `with_max_concurrent_file_transfers`), but PdMount never calls it, so uploads go one file at a time.
  - Block parallelism is fixed at 6 by `ProtonDriveClient::new`; only `from_components` (`client.rs:291`) takes it.
- **Ops.** These are missing:
  - `queue`, `pin`/`unpin`, `cache stats|gc|wipe`, `service`, `mount -o ro` and `sync [<path>]`.
  - `fsync.remote_paths`, `kernel.writeback_cache` and `timeouts.shutdown_grace` are parsed and then ignored.
  - The `pins` table and `cache_blocks.pin` exist, but nothing uses them.
  - Disk eviction (`cache.rs:547`) protects nothing and sorts the whole index.
  - No log rotation.
- **File descriptors.** Every staged file holds an open descriptor (`staging.rs:185`).
  - The hard limit here is **4096**, so an untar of 5k files whose uploads lag behind would hit EMFILE. That makes M4.4 a precondition of the untar benchmark.

1. **Read first:**
   - AGENTS.md;

   - this file's "Ground rules" and your task(s);
   - the DESIGN.md sections the task names.
2. **Do the task, or the batch the Sessions table names.** If the task text conflicts with the code, the code wins for
   line numbers. If it conflicts on behaviour, **stop and record the question in TODO.md Handoff notes**.
3. **Before each commit:**

   - DESIGN.md, docs/decisions.md and TODO.md are updated for what the task changed;
   - the task's checkbox is ticked;
   - Handoff notes are rewritten.
4. **Commit** (D056): one commit per task, even within a batch. The message is `M4.n: <title>` plus the AGENTS.md trailer.
   No push. Record deviations in the commit body and in TODO.md Handoff notes ("Deviations from docs/plans/m4.md").
5. **Never** run real-account tests unless the task says so and the user agreed in that session (D028, D030). Benchmarks
   run on the fake only.

### Ground rules for all tasks

- **Locks (DESIGN.md §4.3, the ranked order in the `engine.rs` module doc).**
  - No lock is held across `.await`.
  - A staging lock comes before the tree lock.
  - Descriptors, files and threads are never closed or joined under the staged-map lock or the tree lock (D032's btrfs flush stall).
- **Service availability (D033, binding):**
  - no test-only switches that bypass the operational rules;
  - background API work stays paced (D027);
  - downloads stay at 5 in flight; uploads stay below 5 files and 6 blocks.
- **Style.** Match the surrounding code: comment density, naming, error enums, `tracing` fields, and the test helpers
  (`engine/tests.rs` `seeded`, `open_with`, `running`, `settle`, `write_file`, `read_file`; `fake_fs.rs` `fake_tree`).
- **Dependencies.** Unsafe code is denied; use `nix`. Add no new crates except where a task names one (M4.1: `hdrhistogram`).
- **SDK fork.** Its files mix CRLF and LF; edit them only with tools that keep line endings.
- **Benchmarks.** `scripts/bench/m4.sh` keeps its state under `BENCH_ROOT` (default `~/.cache/pdmount-bench`, on the btrfs
  disk), not in tmpfs: the SLOs are defined on SSD (§5.7).

## M4.0.1: First security review, whole codebase (Opus orchestrates; reviewers on Fable)

The user moved this review ahead of the M4 work (2026-10-27). It is the application's first security review, so it
covers the whole codebase; M4.16 checks the M4 changes again. Commit: the report summary, D070, TODO (and any Known
gaps) as `M4.0.1: First security review`; there is no code change in this task.

- **Scope:**
  - all four crates (about 33k lines of Rust, tests included);
  - `scripts/` and `tests/` (about 3k lines of shell and Python; they touch the real account and run `rm -rf`);
  - the SDK fork's own changes, `git -C <fork> diff base/0.4.0 pdmount` (P1–P15; record the fork rev reviewed, M4.16 starts from it).
- **Out of scope:**
  - the upstream SDK and other dependencies, beyond how PdMount uses them;
  - dependency advisories: `cargo audit` is not installed, and its database comes from GitHub (D023), so run it only if the user agrees in that session.
- **Threat model first.** Opus writes it, and every reviewer gets it:
  - **Assets:** session tokens and keys (D029), the cache master key, plaintext staging, the encrypted block cache, the user's files.
  - **Actors:**
    - other local users: the socket, file modes, the mount without `allow_other`;
    - other clients, devices and shares of the account, whose names, metadata and content are untrusted input;
    - the network: TLS, and responses the SDK passes through.
  - **Not covered:** root, a compromised Proton server, and other processes of the same uid (except where the design promises more, such as the control socket's peer check).
- **Method.** `/security-review` reviews only a branch's changes, so it does not fit a first review. Instead:
  - Run five read-only Agents with `model: fable` in parallel, each with the threat model and one area:
    1. CLI, daemon, control socket, session, secrets, keyring, login, `notify-send`/`xdg-open` (`crates/pdmount`);
    2. the FUSE adapter and the engine's permission checks, access rules, remote names and paths, `.pdignore` (`pdmount-fuse`; `vfs.rs`, `access.rs`, `pdignore.rs`, `engine/`);
    3. local storage: staging, the cache's crypto and key handling, the store, path construction, file modes, logs (the rest of `pdmount-core`);
    4. the backend: the Proton adapter, integrity checks, error mapping, and the fake and probe kept out of shipped builds by the `fake-backend` feature (`pdmount-backend`, Cargo features, `scripts/ci.sh`'s release build);
    5. the fork's patch diff, plus `scripts/` and `tests/`.
  - Then one Fable verification agent checks every finding against the code and drops false positives.
  - That is six agents, within the workflow size guideline.
- **Rules for the reviewers:**
  - read-only, no real-account calls;
  - never read or print `~/.config/pdcli`, keyrings, tokens or session files (AGENTS.md);
  - each finding has file:line, a concrete attack, a rating and a fix.
- **Handling findings:**
  - High or Critical findings are fixed before M4.1. Each fix is a task `M4.0.2.n`, specified by Opus, with its own commit; ask the user if the fixes are large. M4 then builds on fixed code.
  - Others go to TODO Known gaps with their rating.
  - The threat model is `docs/security/threat-model.md`; the reports go in `docs/security/<date>-review/` (area reports plus `verification.md`), summarised in the TODO handoff note.
  - D070 records the threat model; M4.16 reuses it.

## M4.1: Latency histograms and stats (`metrics.rs`, `pdmount-fuse/src/lib.rs`, `engine.rs`, `control.rs`, `daemon.rs`, `main.rs`, `config.rs`)

DESIGN §5.7–§5.8. New dependency: `hdrhistogram` (workspace, latest 7.x).

1. **Histograms (`metrics.rs`).**
   - Define `pub struct Latency`: one `parking_lot::Mutex<Histogram<u64>>` per key, in µs, range 1 µs–120 s, 3 significant digits.
   - Keys are a fixed `enum Op`, with `as_str`:
     - FUSE: `lookup`, `getattr`, `setattr`, `readdir`, `readdirplus`, `opendir`, `open`, `create`, `mkdir`, `unlink`, `rmdir`, `rename`, `write`, `flush`, `fsync`, `fsyncdir`, `release`, `statfs`, `getxattr`, `listxattr`, `forget`;
     - read, split by source: `read_ram`, `read_disk`, `read_staging`, `read_slow` (anything that waited on the slow path);
     - backend: one key per `Backend` method (`backend_list_children`, …).
   - `Metrics` gains `latency: Latency`.
   - `snapshot_latency() -> Vec<(&str, Summary{count, p50, p90, p99, max})>`; `reset_latency()`.
2. **FUSE timing: from callback entry to the reply call.**
   - Add `pub struct Stopwatch { op: Op, start: Instant, metrics: Arc<Metrics> }`. It records in `Drop`; `set_op(Op)` relabels it (used by `read`).
   - `PdFs::handle` creates it and passes it to the body. Bodies move it into the closure that sends the reply, so it drops right after the reply:
     - `slow`, `retrying` and `committed` take it as a parameter;
     - a hot-path reply drops it at the end of the body.
   - A request answered after a deferred commit therefore counts the commit wait, as §5.7 requires.
   - The read handler sets `read_ram`, `read_disk` or `read_staging` from what `read_local` used. Add a small enum to its return value; no extra locking.
3. **Backend timing.**
   - Add `pub struct TimedBackend { inner: Arc<dyn Backend>, metrics: Arc<Metrics> }` in `pdmount-core`. It implements `Backend` by delegation and records each call's duration under its key. Delegate the default methods too (`fetch_block`, `revisions`).
   - The engine wraps its backend once at construction. `check_not_hot` stays where it is.
   - **New counter `rate_limited`:** calls that ended in `BackendError::RateLimited`, counted in `TimedBackend`. M4.15 needs it.
4. **Gauges.** Computed at snapshot: `queue_pending`, `queue_parked` and `queue_oldest_secs` (from `Journal`; add `oldest_age()`), plus `staged_open_files` (filled by M4.4; 0 until then).
5. **Slow-request log.** When a FUSE request took more than 50 ms and `op` is not `read_slow`, `fsync`, `flush` or `release`, the `Stopwatch` drop logs it at WARN (`op`, `ino` if known, `elapsed_ms`). Rate-limit it to one line per op per 10 s, plus a count of the suppressed ones.
6. **Spans.** `debug_span!("fuse", op, unique = req.unique(), ino)` around the slow-path future (`.instrument`). There is no span on the hot path, which logs nothing per request.
7. **Control and CLI.**
   - `Request::Stats { reset: bool }`. `StatsReply` gains `latency: Vec<LatencyReply{name, count, p50_us, p90_us, p99_us, max_us}>` and `gauges`. Bump nothing; replies are typed (S-L1).
   - `pdmount stats [--json] [--reset]`:
     - the text form prints counters, gauges, then a latency table (`op count p50 p99 max`, µs, ops with count 0 left out);
     - `--json` prints the reply as is;
     - `--reset` clears the histograms after printing.
8. **Prometheus textfile.**
   - Config `[stats] prometheus_textfile = ""` (empty = off; App. B).
   - When set, the daemon writes every 15 s, atomically (temp, then rename):
     - counters as `pdmount_<name>_total`, gauges;
     - latency as summaries `pdmount_latency_seconds{op="…",quantile="0.5|0.9|0.99"}` plus `_count`.
9. **Tests.**
   - `Latency` records and summarises.
   - A `Stopwatch` moved into a deferred closure records once, on drop.
   - A mounted test: `stat` and `mkdir` show up in `stats` with counts > 0, and `--reset` clears them.
   - `TimedBackend` counts `rate_limited` on a fake fault.
   - A config test covers the textfile option.
10. **Docs.** DESIGN §5.8 describes exactly what is measured, and App. B gets `[stats]`.

## M4.2: Fake network profile (`fake.rs`, `main.rs` `FakeCommand`)

DESIGN §15.1 "Planned: bandwidth profiles" becomes real.

1. **The profile.**
   - `pub struct NetProfile { rtt: Duration, up_bytes_per_sec: Option<u64>, down_bytes_per_sec: Option<u64> }`.
   - It is read from `<dir>/profile.json` (`{"rtt_ms":80,"up_bytes_per_sec":20000000,"down_bytes_per_sec":20000000}`) at open, and again when the file's mtime changes.
   - The re-read happens in the same per-call stat pass as `faults.json` (`check_fault_file`), so a running daemon picks up a change.
   - An in-memory fake (tests) uses `set_profile`. `set_latency` stays as it is for the existing tests.
2. **Cost model (per call, slept outside the `State` mutex, before the call's state change).**
   - Every `Backend` call costs one RTT, including the write calls, `poll_events`, `account` and `storage_info`.
   - `list_children` costs one RTT per 150 children, at least one.
   - `get_nodes` costs one RTT per 150 ids.
   - `upload_new`/`upload_revision` cost 3 RTTs (draft, blocks, commit) plus `size / up` on the shared up link.
   - `fetch_block(_into)` costs one RTT plus `len / down` on the down link.
   - **Shared links:** each direction has a `Mutex<Instant>` "busy until". A transfer reserves `[max(now, busy), +len/bw)` and sleeps until its end. This models one 20 MB/s pipe per direction, shared by all concurrent transfers of that process.
   - Two daemons on one fake directory each have their own pipe, which is good enough. Document it.
   - Pause points and faults keep their order relative to the sleep: fault check first, then the sleep, then the operation.
3. **CLI.** `pdmount fake profile [--rtt <ms>] [--up <bytes/s>] [--down <bytes/s>] <dir>` and `pdmount fake profile clear <dir>`. The path goes last (D009).
4. **E19 (fake fidelity under load).**
   - A per-parent child index `children: HashMap<LinkId, BTreeMap<String, LinkId>>` (name → id).
   - It is kept in step by every insert, rename, move, trash, restore and drop, and rebuilt on load and on reload.
   - `child_named` and `list_children` use it.
   - `used` becomes a running total, adjusted when revisions are added or dropped and recomputed at load.
   - Blob reads (`fetch_block*`): take the path and length under the lock, then read in `spawn_blocking` after it is released.
5. **Tests.**
   - With rtt 50 ms, a `list_children` takes at least 50 ms and two concurrent ones overlap (total < 100 ms + slack).
   - Two concurrent 1 MB fetches at 10 MB/s take about 200 ms together.
   - A daemon-style handle picks up a `profile.json` change.
   - An index consistency check (`children` equals a full scan) after a random sequence of operations runs in the existing fake tests' style.
   - All existing fake and engine tests pass unchanged.
6. **Docs.** DESIGN §15.1 replaces "Planned: bandwidth profiles" with the model above. AGENTS.md Commands gets `fake profile`.

## M4.3: Exit benchmark harness (`scripts/bench/m4.sh`, `scripts/bench/slo.py`, `scripts/testdata/make-untar-dataset.sh`)

This task records **D057** (proposed / claude) with the definitions below.

**Setup**
- `scripts/bench/m4.sh [git|untar|read|gc|slo|all]`, default `all`.
- It builds the release binary with `--features fake-backend`.
- It uses `tests/scenarios/lib.sh` with `SCENARIO_ROOT=$BENCH_ROOT/root`, profile `bench`, `BACKEND=fake`.
- It sets `pdmount fake profile --rtt 80 --up 20000000 --down 20000000` before mounting. `RTT_MS`, `UP`, `DOWN` override it.
- Local comparisons run in `$BENCH_ROOT/local/` on the same filesystem.
- Every row writes its numbers to `target/bench/m4-<date>/report.md` (a table: row, mount, local, ratio or value, limit, PASS/FAIL), with raw logs next to it.
- Exit status is non-zero if any row fails.
- It is not part of `scripts/ci.sh`.

**Rows (D057)**

| Row | Procedure | Limit |
|---|---|---|
| `git` | `git clone --mirror https://git.kernel.org/pub/scm/git/git.git $BENCH_ROOT/git.git` once (reused later; the run records its HEAD). Local and mount each `git clone --no-hardlinks --branch v2.50.0 $BENCH_ROOT/git.git <dir>`. Wait for the mount's queue to drain. Run `git status` twice untimed (warm), then 5 timed runs on each side | median(mount) / median(local) ≤ 2.0 |

## M4.9: Disk cache maintenance (`cache.rs`, `engine.rs`, `control.rs`, `daemon.rs`, `main.rs`)

DESIGN §6.2 "Never evicted", §14.2 `cache …`.
1. **Protections.**
   - `DiskCache` gains `protected: HashSet<(LinkId, RevisionId)>`: the base revisions of staged files that are not fully materialized.
   - The engine adds an entry when staging with a base is created or reopened at mount, and removes it when it is fully materialized, removed, or rebased (`set_base_rev`).
   - Eviction skips protected revisions and rows with `pin = 1` (M4.10 sets them).
   - The open-handle soft pin is dropped from §6.2: the kernel page cache and the RAM LRU serve open handles. Write that in DESIGN.
2. **Ordered index (E16).**
   - Keep a `BTreeSet<(last_access, BlockKey)>` next to the map, so eviction pops the oldest entries without a clone-and-sort.
   - `touched` becomes a `HashSet`.
   - RAM hits also touch the disk entry (batched like now), so hot blocks are not evicted from disk first.
3. **Accounting.**
   - `bytes` counts unpinned, sealed file sizes; `pinned_bytes` is counted apart.
   - The watermarks (90 %/80 % of `max_bytes`) apply to `bytes` only (D060).
4. **Orphan sweep.**
   - Once per mount, as a background task (not paced: no API), remove files in `cache/blocks` that have no row, and rows whose file is missing.
   - It works directory by directory and holds the index mutex per directory, not across the walk.
5. **Commands** (daemon required; without one: "not mounted"):
   - `cache stats` prints disk bytes against the cap, entries, pinned bytes, protected revisions, and the pool slots;
   - `cache gc [--target <bytes>]` evicts down to the target (default 80 % of `max_bytes`), never touching pinned or protected blocks, and prints what it freed;
   - `cache wipe [<path>]` evicts every unpinned, unprotected block, or with a path only the blocks of files under it.
   - Control requests: `CacheStats`, `CacheGc{target}`, `CacheWipe{path}`.
6. **Tests.**
   - A protected base is not evicted under pressure.
   - Eviction order follows `last_access`, including RAM-hit touches.
   - The sweep removes an orphan file and a dangling row.
   - gc reaches its target; wipe with a path leaves other files' blocks.
   - The `gc` row of `m4.sh` passes.
7. **Docs.** DESIGN §6.2, §14.2 and §13.2 (the `pin` column now used).

## M4.10: Pins (`engine.rs`, new `engine/pins.rs`, `cache.rs`, `events.rs`, `journal.rs`, `control.rs`, `daemon.rs`, `main.rs`, `status.rs`)

This task records **D060** (proposed / claude).
1. **Model.**
   - A row in `pins (ino, path_at_set, created_at)` (exists, `store/0001.sql`) pins the file, or the whole subtree of a folder.
   - `Node` gains `pinned: bool`: true when the node or an ancestor has a pin row. It is computed at load and recomputed for a subtree on pin, unpin, rename or move (the subtree walk `Tree::subtree` exists).
   - Deleting a pinned node deletes its pin row.
2. **Fetcher.** A background task, woken on change:
   - it walks pinned files whose remote revision is not fully in the disk cache;
   - it fetches their blocks at `Priority::Prefetch` through `cache.get`, which respects `DOWNLOADS` and the prefetch permit;
   - it takes one `Gate::background()` turn per file and per listing (D027);
   - pinned folders not listed yet are listed first, depth-first.
   - Failures back off like the journal, without parking.
   - It waits while the backend is offline or needs a login.
3. **Pinning blocks.**
   - Downloads and `seed` of a pinned file's revision insert rows with `pin = 1`.
   - On a new revision (an event, or our upload's seed), the old revision's rows are set to `pin = 0`.
   - On unpin, the subtree's rows get `pin = 0`.
   - Add `DiskCache::set_pinned(link, rev, bool)`, which updates the rows and `pinned_bytes`.
4. **Triggers.**
   - `pin`/`unpin`;
   - an event that applies a new revision of a pinned file (`events.rs` UpdateContent, after the listing);
   - a node moved into or out of a pinned subtree;
   - startup (resume what is missing).
5. **Space.**
   - Pinned bytes do not count against `cache.max_bytes` (§5.3).
   - `pin` refuses with ENOSPC-style text when the known size of the pinned files exceeds free disk space minus 1 GiB.
   - The fetcher stops when free space drops below 1 GiB and logs a WARN.
6. **CLI.**
   - `pin <path>`, `unpin <path>`, `pin list` (path, files, bytes fetched / known total, state: fetching / complete / waiting-offline);
   - control requests `PinSet{path}`, `PinUnset{path}`, `PinList`;
   - `status` gets `Pinned: N paths, X of Y fetched` when N > 0.
7. **Tests** (engine, fake):
   - pinning a folder fetches all its files' blocks, which survive `cache gc` and pressure;
   - a remote new revision of a pinned file is fetched, and the old one becomes evictable;
   - unpin makes them evictable;
   - a pin survives a restart and resumes;
   - a rename out of the pinned subtree unpins;
   - fetches are paced (paused time, like `prefetch_is_paced_instead_of_bursting`);
   - offline: a pinned file reads with 0 backend calls.
8. **Docs.** DESIGN §5.3 (Pins row), §6.2 (never evicted), §13.2 and §14.2.

## M4.11: Queue tooling and `sync` (`journal.rs`, `engine.rs`, `engine/surface.rs`, `control.rs`, `daemon.rs`, `main.rs`)

This task records **D061** (proposed / claude).
1. **Ids.** Journal entries are identified by inode number (stable, §8.8).
   - CLI: `queue list [<path>]`, `queue show [--id <ino>] [<path>]`, `queue retry|park|drop [--id <ino>] [--all] [<path>]`.
   - Exactly one of `--id`, `--all` or a path is given. The path goes last (D009); a path selects its entry or, for a folder, every entry under it.
2. **list/show.**
   - `list` shows: id, path, kind (upload / create-folder / move / trash / metadata), state (waiting / running / backoff until T / parked: reason), attempts and age.
   - `show` adds the last error, the base revision, and pending dependencies.
   - The data comes from `Journal` (add `entries_under(paths)`, under the journal lock, with paths resolved first under the tree read lock).
3. **retry.** Clears park and backoff, then `force` and wake (the functions exist).
4. **park.** Marks the entry parked with the reason "parked by user". Like automatic parks, it lives in RAM: a remount or `retry` resumes it. Document this in D061.
5. **drop** (requires `--yes`; prints what it discards first). It discards the local intent of each selected entry:
   - a node with a remote counterpart goes through the keep-remote path of `conflicts resolve` (`engine/surface.rs` `resolve_keep_remote`, D045): remove the staging and the pending namespace change, then relist the parent;
   - a local-only node (never uploaded) is removed locally, with its subtree;
   - kernel invalidations go through the usual queue.
   - It is refused for an entry whose upload is running ("retry later").
6. **`sync [<path>]`.** Forces every entry under the path (or all), then waits until none is pending.
   - It prints the parked ones and exits 1 if any are parked or the 10 min timeout (`--timeout <s>`) expires.
   - Control request `Sync{path, timeout_secs}`. Reuse `drain`'s waiting (generalise it to a path filter).
7. **Tests.**
   - list and show of each kind;
   - retry of a parked entry uploads it;
   - park holds an entry until retry;
   - drop of a modified remote file restores the remote content on read;
   - drop of a local-only file removes it;
   - drop of a folder subtree;
   - `sync <dir>` returns after only that subtree's uploads;

### M4.6.1: Store writes (E2, E12)

### M4.6.2: Staging without a sidecar for new files; data and WAL flushed in parallel (D067)

This task records **D067** (proposed / claude): "A staging file without a base has no sidecar; `local` fsync flushes
data and store in parallel".

1. **Sidecar only with a base.**
   - `Staged` keeps `sidecar_on_disk: bool` and `sidecar_synced: bool`.
   - `StagingDir::create` writes the sidecar only when `base_rev` or `base` is `Some`, and then **before** creating
     the data file. A data file without a sidecar then never had a base.
   - `save()` (`set_base_rev`, materialize, truncate) writes it whenever the sidecar is not the default, and sets
     `sidecar_on_disk = true, sidecar_synced = false`.
   - When the sidecar becomes the default again (all blocks materialized, `base = None`, no `base_rev`), keep
     saving it as now. Don't delete it: one rule is enough.
2. **Startup.**
   - `staged_inos` lists the **data files** (names that parse as an inode number), not the `.state` files. Without
     this, restart treats a pending new file as missing and recreates it empty: data loss. A `.state` without a
     data file is removed.
   - `reopen` treats a missing sidecar as the default (no base, no `base_rev`, nothing materialized).
   - Staging from older versions always has a sidecar, so it reopens unchanged.
3. **Removal.** `StagingDir::remove` ignores NotFound for the sidecar.
4. **`Staged::sync`.**
   - When `sidecar_on_disk && !sidecar_synced`: fdatasync the sidecar **first**, then the data, so durable data
     never comes with a lost sidecar that held a base. Then set `sidecar_synced`.
   - Otherwise only the data.
5. **`Engine::fsync` (`engine.rs` `fsync`).**
   - The staging sync (`spawn_blocking`) and `self.store.flush()` run together (`tokio::join!`). The deferred
     error is still taken and persisted before the flush starts.
   - Both results are checked: data first, then store.
   - In a comment: ordering between the two is not needed, since the reply waits for both, and a row can reach the
     disk earlier through any other durable commit anyway.
6. **Tests** (`staging.rs`, `engine/tests.rs`):
