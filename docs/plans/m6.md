Task specifications for milestone M6 (D077, D099). Status and checkboxes live in `TODO.md`; reasons in `docs/decisions.md`; the
specification in `DESIGN.md` (§10.8, §15.3 scenario X6, §16). A UI for resolving conflicts is out of scope and not decided.

## Context

Today (§10.8, `crates/pdmount/src/daemon/stop.rs` `announce_conflicts`, `notify.rs`): a `notify-send` at most every 30 s saying
"N new conflicts; see `pdmount conflicts list`", also for `notice` conflicts the engine already settled. Nothing is kept: with
no session bus at that moment, the notification is lost.

## M6.0.1: SDK fork rebase onto upstream `v0.5.1` (D099)

The fork sits on `base/0.4.0` (`docs/sdk-patches.md`, "Fork repository"); upstream `tirbofish/proton-sdk-rs2` has tagged `v0.5.0`
and `v0.5.1`, and its maintainer suggests updating. The work is in the fork's working copy (`PDMOUNT_FORK_CHECKOUT` in
`.pdmount-local.env`).

1. `git fetch upstream`; read `v0.4.0..v0.5.1` (changelog and the diff of `proton-drive-sdk` and `proton-sdk-rs2`): API changes,
   new features (shares, devices, photos, events), crypto changes (Q5), and anything that fixes what a patch fixes.
2. Per patch P1–P18, decide and record in `docs/sdk-patches.md`: **merged upstream** (drop), **superseded** (upstream does it
   differently: drop it and adapt PdMount), or **still needed** (rebase its branch onto `v0.5.1` as one self-contained,
   upstream-ready branch with its tests). Tag `base/0.5.1` and build a new integration branch, `pdmount-0.5`, from the rebased
   branches with `--no-ff` merges, as `pdmount` was built. Old branches, `base/0.4.0` and every `pin/*` tag stay, so old
   PdMount commits still build.
3. The fork's tests pass, the patches' own tests included.
4. PdMount on the new fork: while working, an untracked local cargo override (`--config` patch to the working copy), so
   nothing is pushed early; adapt `pdmount-backend`'s `proton` adapter to API changes; then move the `[patch.crates-io]` pin
   in `Cargo.toml` to the new integration commit, tagged `pin/<short>`.
5. Checks: the full `scripts/ci.sh`; then, with the user's consent at that point (D030), the Q1/Q6 probe (`cargo test -p
   pdmount probe -- --ignored`, about a minute, writes only under `pdmount-test/q1/`) and a short real-account scenario set
   (`r1`, `g3`, `a1` at small sizes, `live`, stopping at the first 429).
6. Publication: pushing the fork's branches, `base/0.5.1` and the `pin/*` tag needs the user's agreement and goes before
   the PdMount commit that pins it. Until then PdMount's pin stays on the old fork commit.
7. Docs: `docs/sdk-patches.md` (base row, tracking table, behaviour changes from upstream), DESIGN §2 where upstream
   changed a finding, AGENTS.md's citation table (`sdk/`, `rs2/` at 0.5.1), Q5 in `TODO.md` if upstream says anything
   about the crypto migration.

## M6.0.5: Evaluation of the community SDK `narrrl/proton-sdk-rs`

Added by the user (2026-11-18). PdMount builds on `tirbofish/proton-sdk-rs2` through a patched fork (D002); no document has
evaluated the other community SDK, [`narrrl/proton-sdk-rs`](https://github.com/narrrl/proton-sdk-rs). This task is research only:
nothing switches, and no code, `Cargo.toml` or fork changes. It runs after M6.0.1 (the rebase, with P19), so the comparison is
against `pdmount-0.5`; it can run alongside M6.0.2 and M6.0.3. Its recommendation goes to the user before M6.0.4 picks
M6.0.2's findings, since a switch changes where a fix belongs (a fork patch, or narrrl's SDK), and it may reshape later
SDK-dependent work (the crypto migration, Q5; upstream PRs, D089).

**Starting point, unverified** (narrrl's README, CHANGELOG and `UPSTREAM_SYNC.md`, read 2026-11-18): a pure-Rust rewrite in two
crates, `proton-sdk` (session, HTTP, crypto) and `proton-drive-rs`, 0.12.1, MIT, one maintainer, last commit 2026-11-15; it powers
the FUSE client `narrrl/proton-drive-linux`; crypto is rPGP only (no Go, clang or protoc, which D004 lists as build needs); a per-commit sync log

## M6.0.6: Unverified signatures (D132 amended by the user)

Builds D132's amendment on fork P27, after the pin includes it. The adapter reports a node's failed signature parts and a
digest of what they cover with the node (`RemoteNode`), instead of only logging them; the engine keeps found nodes in the
tree's store (schema 5) and applies the root's mode: `refuse` answers EACCES to open, rename, move and delete of such a
node and to creates and moves into a folder whose key or hash key failed, until it is accepted; `warn` only records it.
Commands over the control socket: `signatures list [--json]`, `signatures accept <id>` and `signatures check [<path>]`
(every folder under the path, or the mount, listed again and its nodes checked, paced as a §9.4 refresh on background
turns; progress and a summary; path last, D009). Notification through `notify.rs` (moves to D-Bus with M6.1): per tree at most every 10 minutes, the count and
`pdmount signatures list`, no names. `status` line, config keys in Appendix B, user guide. Tests: a fake fault that marks
a node unverified (each part), the refusals and their errno, accept with the same and a changed digest, the store across a
remount, `check` finding a node in a folder never listed, the notification's text and rate. Full CI (engine, store, FUSE layer).

## M6.0.7: Signatures verified at server time, a bounded offset (M6.0.3 V-8, V-9, user)

Added by the user on 2026-11-19 and done before M6.0.6, whose refusals would otherwise also catch a node signed in the
last seconds when the device clock is slow (`docs/security/2026-11-18-review/verification.md`, V-8). The fork signs
and makes keys at `server_time::check_now()` but verifies at the device clock (`Verifier::default()` and the decryptors
that verify), and rPGP refuses a signature dated after that time. Fork patch P29, a branch `0.5/fix/verify-at-server-time`
from `base/0.5.1` (or on P19 if it needs its clock): every verification in the SDK takes `.at_date(check_now())`, the
block bodies, the content key, node and share keys, names, extended attributes, memberships, and anything else that
verifies. First read how the official clients date a verification (`cs/`) and follow them. Tests in the fork, written
first and failing before: with the offset set so server time is ahead of the device, a block, a content key and a
name signed at server time verify; a signature dated after server time still fails. PdMount: the pin move, the P29
section in `docs/sdk-patches.md`, the Known gaps entry closed; no PdMount code unless the adapter needs it.

V-9, accepted by the user on 2026-11-19 with the design below: once verification takes server time, a wrong offset
also makes fresh signatures fail or future-dated ones pass. A P19 amendment (its branch, `server_time.rs`):
- The offset is taken only from the Drive API host's answers, not from block storage, public links or other hosts.
- The first offset after a start is adopted when it is within a day of the device clock; beyond that it is refused with
  a WARN and the device clock is used. A day covers a hardware clock kept in local time (up to ±14 h) and a machine
  without time sync; a minute would refuse exactly the clocks the offset exists to correct.
- Later, a change of more than about a minute is adopted only when a second Drive API answer confirms it; until then
  the old offset stays, with a WARN. A real correction (NTP stepping the device clock) is confirmed by the next answer.
  Changes below that, down to P19's 2 s rule, are adopted as now.
- `doctor` shows the offset in its clock line (PdMount; DESIGN and the decision that covers `doctor`'s lines amended).
Tests in the fork, written first: a far-future and a far-past first answer refused; a 2 h first offset adopted; a jump
of 10 min held until a second answer agrees, one odd answer between two right ones changing nothing; storage-host
answers ignored. Real account: none beyond the usual (the server's dates are the input). Full CI.

## M6.0.11: Large-file reads (user)

Picked by the user on 2026-11-19 after the slow-video diagnosis (`TODO.md`, the parked entry; a ~650 MiB phone MP4 took
minutes to appear from the Photos mount; the fake gave 1–12 s, set by the rate). Three changes:
- **Photos readahead.** The Photos tree reads one block per round trip (`photos.rs`, no readahead); give it the engine's
  per-handle sequential detector and readahead permits (none for scan reads, as in the engine), so a video plays at the
  link's rate.
- **Block lists by range.** The adapter lists every block of a revision in pages of 10 (fork `DEFAULT_BLOCK_PAGE_SIZE`)
  before the first byte, again after `BLOCK_MAP_TTL` (10 min) mid-read, and the thumbnail task lists every block of every
  video. List only the pages a read needs (the API takes `FromBlockIndex` and `PageSize`; block offsets from the XAttr's
  block sizes, P4), each page cached with its own expiry, so an expired page is listed again alone; take the page size
  the official clients use if larger (check `cs/` and what the API accepts); the thumbnail path lists no content blocks
  (DESIGN §14.5 says one request per photo). A fork change if the fork's API needs one (P30, or an amendment of P3/P4).
- **Readahead held until the pattern is known.** In My Files the detector starts after two adjacent reads, which the
  kernel's 128 KiB reads make immediate, so blocks 1–2 compete with a jump to the moov at the end (first frame about
  twice as late). Start readahead only once a read crosses into the next block (or another rule that keeps sequential
  copies fast); measure both.
Tests on the fake (its block listing must charge a round trip per page, or the range change cannot be seen); the
diagnosis' measurements again (first frame, throughput at 20/5/2 MB/s, moov at the end, faststart, MKV, Photos and My
Files). Decision D135 for the choices. Full CI.

## M6.2: Conflict notifications

- Only `open` conflicts notify; `notice` ones stay in the log and `conflicts list`. Summary "PdMount: conflict"; body: the
  file's path and what happened, in plain words per kind (`edit_edit`: "changed here and on another device; both copies kept").
- One notification per conflict, up to three per 30 s; the rest are summed in one ("5 more conflicts") through `Coalescer`.
- Actions, on servers that have them: **Show** opens the conflict copy's folder (`org.freedesktop.FileManager1.ShowItems`, then
  `xdg-open` on the folder). The daemon listens for `ActionInvoked` and `NotificationClosed` while notifications are open.
- A body without the file name is one setting away: `notify.conflict_names = false` (lock screens); `notify.conflicts = false`
  turns them off. Add both to Appendix B.
- Body text is escaped: the Notifications spec allows markup, and names come from other devices (remote input, D070).

## M6.3: Missed conflicts

`conflicts` gains `notified_at` (a store migration). A conflict is marked when its notification is accepted by the
service, so it is shown at most once. When the daemon starts, or when the bus or the notification service appears
(`NameOwnerChanged`), `open` unnotified conflicts go out, summed if more than three. A conflict resolved in between is
not shown. A daemon with no session bus retries connecting every 60 s, and `Show` works only with a bus, naturally.
Existing rows migrate as notified, so nothing old pops up.

## M6.4: Slow-download notification (D137, user)
