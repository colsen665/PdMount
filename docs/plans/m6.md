specification in `DESIGN.md` (§10.8, §15.3 scenario X6, §16). A UI for resolving conflicts is out of scope and not decided.

## Context

Today (§10.8, `crates/pdmount/src/daemon/stop.rs` `announce_conflicts`, `notify.rs`): a `notify-send` at most every 30 s saying
"N new conflicts; see `pdmount conflicts list`", also for `notice` conflicts the engine already settled. Nothing is kept: with
no session bus at that moment, the notification is lost.

## M6.0.1: SDK fork rebase onto upstream `v0.5.1` (D099)

The fork sits on `base/0.4.0` (`docs/sdk-patches.md`, "Fork repository"); upstream `tirbofish/proton-sdk-rs2` has tagged `v0.5.0`
and `v0.5.1`, and its maintainer suggests updating. The work is in the fork's working copy (`PDMOUNT_FORK_CHECKOUT` in
`.pdmount-local.env`).

1. `git fetch upstream`; read `v0.4.0..v0.5.1` (changelog and the diff of `proton-drive-sdk` and `proton-sdk-rs2`): API changes,
   new features (shares, devices, photos, events), crypto changes (Q5), and anything that fixes what a patch fixes.
2. Per patch P1–P18, decide and record in `docs/sdk-patches.md`: **merged upstream** (drop), **superseded** (upstream does it
   differently: drop it and adapt PdMount), or **still needed** (rebase its branch onto `v0.5.1` as one self-contained,
   upstream-ready branch with its tests). Tag `base/0.5.1` and build a new integration branch, `pdmount-0.5`, from the rebased
   branches with `--no-ff` merges, as `pdmount` was built. Old branches, `base/0.4.0` and every `pin/*` tag stay, so old
   PdMount commits still build.
3. The fork's tests pass, the patches' own tests included.
4. PdMount on the new fork: while working, an untracked local cargo override (`--config` patch to the working copy), so
   nothing is pushed early; adapt `pdmount-backend`'s `proton` adapter to API changes; then move the `[patch.crates-io]` pin
   in `Cargo.toml` to the new integration commit, tagged `pin/<short>`.
5. Checks: the full `scripts/ci.sh`; then, with the user's consent at that point (D030), the Q1/Q6 probe (`cargo test -p
   pdmount probe -- --ignored`, about a minute, writes only under `pdmount-test/q1/`) and a short real-account scenario set
   (`r1`, `g3`, `a1` at small sizes, `live`, stopping at the first 429).
6. Publication: pushing the fork's branches, `base/0.5.1` and the `pin/*` tag needs the user's agreement and goes before
   the PdMount commit that pins it. Until then PdMount's pin stays on the old fork commit.
7. Docs: `docs/sdk-patches.md` (base row, tracking table, behaviour changes from upstream), DESIGN §2 where upstream
   changed a finding, AGENTS.md's citation table (`sdk/`, `rs2/` at 0.5.1), Q5 in `TODO.md` if upstream says anything
   about the crypto migration.

## M6.0.2: Parity check against the official SDK (D099)

A read-only report on the rebased fork.

1. Update the reference checkout (`PDMOUNT_CS_SDK`) to the newest official tag (`js/v0.23.0` when planned; take the newest
   then) and the `cs/` row of AGENTS.md's citation table.
2. Compare area by area, citing `cs/…:line` at the new tag and `sdk/…`, `rs2/…` or `crates/…` on our side:
   - **operational rules** of `cs/README.md` (polling intervals, number of volumes, client identification headers, rate
     limits, backoff, what clients must not do) against PdMount's event poller, retries (P12), concurrency (P7, P18) and
     headers;
   - **write path:** file and revision drafts, `ClientUID`, block upload and verification tokens, the manifest signature,
     XAttr contents (size, mtime, digests), commit, conflict codes (Q1, Q6, D043), name hashes on rename and move (P14);
   - **read path:** block map pagination (P1), digest and manifest verification (P2, P17), thumbnails;
   - **namespace:** trash, delete, restore, move and rename, folder mtime (P5);
   - **events:** event types, refresh, `more`, per-volume polling, and what changed since 0.21;
   - **auth and keys:** session refresh (P9), address keys, passphrase handling, the crypto changes behind Q5;
   - **further roots** (for M5.9–M5.14): the shares, devices and photos APIs as the official client uses them.
3. Output: `docs/sdk-parity.md`, one table per area: official behaviour, fork, PdMount, status (same, differs, missing,
   not applicable), severity, proposed action (a new patch P19…, a PdMount change, or accepted with the reason). A finding
   that affects correctness or the service rules is High.
4. Nothing else changes in this task.

## M6.0.3: Security review (D099; Opus orchestrates, reviewers on Fable)

Added by the user (2026-11-12). It can run alongside M6.0.2, after M6.0.1. Method as M4.0.1 (`docs/plans/m4.md`): every
reviewer gets the threat model (`docs/security/threat-model.md`, D070), read-only Agents with `model: fable` in parallel,
one per area, then one Fable verifier that checks each finding against the code and merges duplicates. Report in
`docs/security/<date>-review/` (area reports, `verification.md`); the threat model is updated where the scope grew.

- **Scope:** what changed since the M4.16 review (`docs/security/2026-10-31-review/`), and the new SDK base:
  1. supervisor and services: `supervise.rs`, `service.rs`, the unit files and goldens (`$PATH`, quoting, argv,
     file modes, the elogind drop-in that is printed, `unmount --if-stale`, `--clear-stale`);
  2. the stop path and the system bus: `flush.rs`, `logind.rs` (`zbus`, accepting only logind's signals), `resume.rs`,
     notifications (`notify.rs`), the daemon's start and stop;
  3. the pending marker: `engine/marker.rs`, `incoming.rs` (untrusted JSON from other devices, bounds, the read-only
     `.pdmount`, names in notifications and `status`);
  4. the release pipeline: `dist-workspace.toml`, `.github/workflows/{ci,release}.yml`, `.github/build-setup.yml`,
     `about.toml`/`about.hbs` (actions, permissions, triggers, tag pushes, what the archive contains, leaked paths);
  5. the SDK: the rebased patches (`git -C <fork> diff base/0.5.1 pdmount-0.5`) and upstream's changes `v0.4.0..v0.5.1`
     where PdMount uses them (crypto, verification, logging of secrets: P16, P17), with the fork revision recorded.
- **Out of scope:** what M5.8 will review (M5.9–M5.14, not yet written); other dependencies beyond how PdMount uses them;
  `cargo audit` only if the user agrees in that session.
- **Output:** findings ranked Critical, High, Medium, Low, each with file:line, a failure or attack scenario and a fix.
  Commit: the reports, the threat model, `TODO.md` Known gaps for what is not fixed (`M6.0.3: Security review`), no code.
  M5.8's review then covers only what changed after this one.

## M6.1: D-Bus client

`org.freedesktop.Notifications` through `zbus` (pure Rust; the D-Bus library D042 and D071 declined, now justified by D077;
it arrives in M5.1 for logind, D091). The shutdown notification of D091 moves too.
`GetCapabilities` decides whether buttons are offered. No session bus or no notification service: as today, nothing fails or
waits. The sign-in notification moves too. `notify-send` goes away, and with it file names in `/proc/<pid>/cmdline`. `doctor`
reports the service instead of the tool. Check `zbus`'s dependency tree against the review's threat model (D070).

## M6.2: Conflict notifications

- Only `open` conflicts notify; `notice` ones stay in the log and `conflicts list`. Summary "PdMount: conflict"; body: the
  file's path and what happened, in plain words per kind (`edit_edit`: "changed here and on another device; both copies kept").
- One notification per conflict, up to three per 30 s; the rest are summed in one ("5 more conflicts") through `Coalescer`.
- Actions, on servers that have them: **Show** opens the conflict copy's folder (`org.freedesktop.FileManager1.ShowItems`, then
  `xdg-open` on the folder). The daemon listens for `ActionInvoked` and `NotificationClosed` while notifications are open.
- A body without the file name is one setting away: `notify.conflict_names = false` (lock screens); `notify.conflicts = false`
  turns them off. Add both to Appendix B.
- Body text is escaped: the Notifications spec allows markup, and names come from other devices (remote input, D070).

## M6.3: Missed conflicts

`conflicts` gains `notified_at` (a store migration). A conflict is marked when its notification is accepted by the
service, so it is shown at most once. When the daemon starts, or when the bus or the notification service appears
(`NameOwnerChanged`), `open` unnotified conflicts go out, summed if more than three. A conflict resolved in between is
not shown. A daemon with no session bus retries connecting every 60 s, and `Show` works only with a bus, naturally.
Existing rows migrate as notified, so nothing old pops up.
