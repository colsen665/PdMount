# M5 implementation plan: user services, flush at session end, further roots

Task specifications for milestone M5 (D073–D076, D078–D081, D091, D097). Status and checkboxes live in `TODO.md`; reasons in
`docs/decisions.md`; the specification in `DESIGN.md` (§14.4, §14.5, §15.3 scenarios X1–X5, X7–X11, §16).

## Context

M4 gives M5 three things: the upload barrier of `sync` (M4.11), the shutdown wait and the `shutdown_grace` key (M4.12,
D062) and the autostart entry (M4.13). M5 starts after M4 is ticked.

Written while M4.8 is open, so `DESIGN.md` Appendix B does not list `timeouts.shutdown_grace`'s new default or the
`[service]` key yet: M5.1 and M5.7 add them.

Working method (user, 2026-11-12): `docs/multi-task-runs.md` (D098); as D056, one commit per task (`M5.n: <title>`), implemented by agents of the Model column
below, merged with the full CI where `TODO.md` marks a task `[full]`.

## Facts and unknowns

Verified on the Gentoo machine (2026-10-30):
- OpenRC 0.63.3 loads user services from `/etc/user/init.d` and `${XDG_CONFIG_HOME}/rc/init.d`; `rc-* --user` manage them.
- `pam_openrc.so` is in `/etc/pam.d/system-login`, and the machine's user session already runs `dbus` under
  `supervise-daemon`. No `user.<name>` link is in a runlevel.
- `/etc/init.d/user` has no `depend()`, so nothing orders the user session against `net` at shutdown.
- `/etc/user/init.d/dbus` exports `DBUS_SESSION_BUS_ADDRESS` only inside its own script, so a unit must set it itself.
- elogind's `InhibitDelayMaxSec` is the default of 5 s.

Not verified; M5.0 answers these:
1. **OpenRC logout:** does the last `pam_close_session` stop the user services? (The module's strings suggest a session
   count, but this has not been observed.)
2. **OpenRC shutdown:** does SIGTERM reach a user service before the network goes down, and how long may it take?
3. **systemd logout and shutdown:** the same questions on Debian, including whether `user@.service`'s own stop timeout
   caps the unit's `TimeoutStopSec` and how `UserStopDelaySec` delays the stop.
4. **Per-user network:** does a Wi-Fi connection owned by the user survive until the flush ends?
5. **Respawn:** does `supervise-daemon` respawn a daemon that exited cleanly after `pdmount unmount`?
6. **Inhibitors:** logind's `delay` lock is capped (5 s by default) and its `block` lock refuses the shutdown rather
   than delaying it. Is either useful when the probe shows SIGTERM arriving too late?

## M5.0: Probe

A small script (`scripts/repro/session-end-probe.sh`), installed by the user as a user service on each system. On
SIGTERM it logs a timestamp, whether a test host answers, and whether the session bus is there, then keeps logging once
a second until it is killed. The user runs: logout, `loginctl reboot` and `poweroff` from a shell, on Gentoo and
Debian. Outcome: answers to the six unknowns in a new section here, and a decision if they change D074 or D075.
If SIGTERM arrives after the network is gone on a system, M5.1 cannot flush there at shutdown as specified: bring the
result to the user before M5.1.

**Outcome (2026-11-12):** results below; D091 amends D075: the flush also starts at logind's PrepareForShutdown, under a
delay lock. Question 5 (respawn) is for M5.3 to apply: `supervise-daemon` restarts after any exit, systemd's
`Restart=on-failure` not after exit 0.

### Running the probe

The script is standalone: copy `scripts/repro/session-end-probe.sh` to the Debian machine if the repository is not there.
Its header lists what it logs. Each check is a DNS lookup and a TCP connect to `drive-api.proton.me:443`, closed without
sending data. It runs once a second after a signal and once at start; there are no network checks in between. After a
signal it keeps running for up to 120 s (`PROBE_LINGER`), so each logout or shutdown test can take up to about 2.5 min
unless the system kills it sooner. That cutoff is what the test measures.

On each system, logged in to the graphical session as the desktop user (the usual login through the display manager),
with no other session of that user open (no ssh or tty login): a second session can keep the user services running at
logout, which would hide the answer to question 1 or 3. Run every command in a terminal window inside that session
(xterm or similar). It is the case the daemon will meet: the user at the desktop, the session's services running.

1. `session-end-probe.sh install openrc` (Gentoo) or `install systemd` (Debian). Then `session-end-probe.sh summary`
   shows a `start` line.
2. **Logout:** end the graphical session the usual way (the desktop's or window manager's logout or exit, not the display
   manager's menu), wait a minute at the display manager, log in again (questions 1 and 3). On Debian, lingering must be off
   (`loginctl show-user` shows `Linger=no`).
3. **`loginctl reboot`** (elogind, Gentoo) or **`systemctl reboot`** (systemd, Debian; its `loginctl` has no `reboot`) in
   the terminal, as the user, then log in (questions 2 and 3). Both go through logind, as a desktop's reboot entry would,
   so PrepareForShutdown and delay locks apply.
4. **`poweroff`** in the terminal as root (`su -c poweroff` or `sudo poweroff`; on OpenRC this skips logind, on systemd
   it is `systemctl poweroff` and still asks logind first), then start the
   machine and log in (questions 2 and 3).
5. **Respawn** (question 5): `pkill -USR1 -f 'session-end-probe.sh run'`, wait 15 s, then `pkill -USR2 -f
   'session-end-probe.sh run'`, wait 15 s. A new `start` line after an `end reason=usr1` means a clean exit was restarted.
6. **Inhibitor** (question 6): `session-end-probe.sh uninstall`, `install openrc|systemd --inhibit`, then repeat step 3.
7. **Per-user Wi-Fi** (question 4), only on a machine with a Wi-Fi connection limited to the user (`conns=` shows
   `802-11-wireless:user`): repeat steps 2 and 3 on that connection.
8. `session-end-probe.sh summary`; paste its output into the session, then run `session-end-probe.sh uninstall`.

The summary has no file names, host names or user names: pids, boot ids, times, connection types and check results only.

### Results: Gentoo (2026-11-12)

OpenRC 0.63.3, elogind 255; two series of runs, the second on fresh boots. All network connections were system-owned.
Second series, times relative to the probe's first SIGTERM:

| Run | Before SIGTERM | After SIGTERM | End of the probe |
|---|---|---|---|
| Logout | — | X session ends +4.8 s; network and session bus up throughout | its own 120 s limit; nothing killed it. The next login started a new one |
| `loginctl reboot` | PrepareForShutdown 1.3 s before | X session ends +7.1 s; NetworkManager gone +9.8 s; session bus gone +12.3 s; TERM again +15.0 s, +16.1 s | killed after +16.3 s |
| `poweroff` as root | no PrepareForShutdown | +7.9 s, +11.8 s, +14.4 s; TERM again +16.4 s, +17.4 s | killed after +17.7 s |
| `loginctl reboot`, delay lock held | PrepareForShutdown 6.3 s before; the shutdown starts after 5 s (`InhibitDelayMaxSec`) | +6.7 s, +11.3 s, +12.6 s; TERM again +15.6 s, +16.6 s | killed after +16.9 s |

A DNS lookup and a TCP connect to the API host succeeded at every check, up to the end, in every run of both series.

1. **Logout:** SIGTERM at once (the user runlevel switches to `shutdown`), and the user runlevel waits for the service:
   the probe ran its full 120 s with the network and the session bus up. The flush works at logout as D075 specifies.
   The first series' logout got no SIGTERM, in a boot whose user runlevel already read `shutdown` when the probe was
   started; not explained, not seen on fresh boots.
2. **Shutdown:** SIGTERM arrives at the start, with the network up, and the network stays up to the end. But the
   service is killed about 16 s later, not after 90 s: every shutdown sends TERM again at +15.0 to +16.4 s and kills
   about a second later. Inferred from the order above and the init scripts: the shutdown stops `user.<user>` (started
   by `pam_openrc`, in no runlevel, no `depend()`) without waiting for the user services, stops its own services, then
   `killprocs` sends TERM and KILL to what is left. The unit's `retry` has no effect, and the 15 s are how long this
   machine's services take to stop, not a setting.
5. **Respawn:** `supervise-daemon` restarts after exit 0 and after exit 1, 5 to 6 s later (`respawn_delay`). Exit codes
   cannot keep the daemon stopped: M5.3's `unmount` must stop the service or refuse.
6. **Inhibitors:** a logind-initiated shutdown (`loginctl reboot`, as a desktop's reboot entry) sends PrepareForShutdown
   and honours a delay lock: elogind waited its `InhibitDelayMaxSec` (5 s by default) before starting the shutdown, with
   network and session bus up. Root's `poweroff` bypasses logind. (The first series' reboots sent no PrepareForShutdown,
   so they presumably did not go through logind.)
4: a per-user Wi-Fi connection is not available on the Gentoo machine.

### Results: Gentoo, raised delay limit (2026-11-12)

`InhibitDelayMaxSec=180` in a drop-in under `/etc/elogind/logind.conf.d/`, loaded at boot (the probe's start line read
`inhibit_delay_max=180s`), probe installed with `--inhibit`, then `loginctl reboot`:
- PrepareForShutdown, then 120 s with nothing stopped: every check showed the system runlevel `default`, the network,
  NetworkManager and the session bus up, and no SIGTERM. The desktop stayed usable.
- The probe ended itself at +120.9 s and with it released the lock. The next boot's kernel started 46.6 s later, before
  the 180 s limit would have run out, so elogind went on when the lock was released, not at the limit.
- `supervise-daemon`'s respawn did not show in the log during that shutdown.

So a daemon holding a delay lock gets up to `InhibitDelayMaxSec` before anything stops, and ends the wait itself by
releasing the lock. The default limit is 5 s; raising it needs root. Root's `poweroff` and `reboot` bypass logind.

## M5.1: Flush on SIGTERM

1. On SIGTERM, SIGINT or SIGHUP, the journal takes a barrier over the queue as it is (the same one `sync` uses), skips the
   upload debounce for the entries behind it, and keeps running until the barrier is reached or
   `timeouts.shutdown_grace` (default 90 s; was 30 s) has passed.
2. Dirty kernel pages come first: `syncfs` on the mount before the barrier, on a blocking thread with its own short
   deadline. `write()` has already reached the daemon (no writeback cache, D083), but pages dirtied through a shared writable
   mmap stay in the kernel until msync, munmap or the kernel's writeback. From reading the kernel; the tests cover it.
3. New writes are still accepted (D062) and stay pending; they do not extend the wait.
4. No wait while offline or in `needs_login`; parked entries are not waited for. Rate limits and backoff apply as usual:
   the flush does not hurry past HTTP 429, and the deadline simply ends it.
5. At the barrier or the deadline, the steps of D062 follow: stop starting steps, commit the store, unmount lazily.
   `unmount --wait` keeps its 10 minutes. `unmount --force` waits `shutdown_grace + 30 s` before SIGKILL (M4.12).
6. Log: "flushed N entries in T s" or "N entries left for the next mount".
7. **logind (D091):** at mount, take a delay lock for `shutdown` (`org.freedesktop.login1.Manager.Inhibit`, `"shutdown"`,
   `"delay"`; the lock is the returned fd) and watch PrepareForShutdown on the system bus. On `true`, start steps 1–6, with
   the grace counted from then; a later SIGTERM continues the same flush. Close the fd when the flush ends or the grace runs
   out, and at once with an empty queue, offline or in `needs_login`. On `false` (cancelled), take a new lock; the daemon
   keeps running. No system bus, no logind or a refused lock: log it once and rely on SIGTERM.
8. **Notification (D091):** a non-empty queue at PrepareForShutdown sends "PdMount: uploading N changes before shutdown"
   through the existing notification path; never waited for.
9. **D-Bus client:** `zbus` (M6.1's choice, D077) comes in here for the system bus. Check its dependency tree against the
   threat model (D070); the notifications stay on `notify-send` until M6.1.

Tests: X1–X3 and X11 on the fake with the network profile; X11 runs a stub logind on a private bus
(`DBUS_SYSTEM_BUS_ADDRESS`); journal unit tests for the barrier and debounce; `kill9` unchanged.

**Outcome (2026-11-12):** built as specified; the open details are D092 (accepted 2026-11-13): one grace for the flush and the wait for
running steps, back-offs kept by the barrier, the daemon stays mounted after a PrepareForShutdown flush, a second signal ends
the wait, SIGHUP stops (D026's SIGHUP part superseded), `zbus` 5.19. Code: `crates/pdmount/src/flush.rs`, `logind.rs`,
`Engine::flush_barrier`/`flush_to`; scripts `tests/scenarios/x1.sh`–`x3.sh`, `x11.sh` (stub: `pdmount fake logind`, test
builds). X1 includes a page dirtied through a shared mmap that only the `syncfs` uploads (checked: without it, X1 fails).

## M5.2: Warning at start

The queue left at the last stop is known at mount. When it is not empty, the daemon logs a WARN and sends a desktop
notification: "PdMount: N changes from the last session are still uploading". A later notification says when they have
finished only if the first one went out. An unclean stop (crash) with a non-empty queue warns the same way. `status`
already shows the queue. Test: X4 with a notification stub on `PATH`.

## M5.3: Under a supervisor

- Readiness: `mount --foreground` reports ready after the mount answers: `NOTIFY_SOCKET` (`READY=1`, a plain datagram, no
  library) and `--notify-fd <n>` for OpenRC's `notify="fd:3"`.
- Stale mount: a `--clear-stale` option on `mount --foreground` runs the check and `fusermount3 -uz` of `unmount --force`, but
  only when no daemon of the profile answers.
- `pdmount unmount` under a supervisor: depending on M5.0's respawn answer, either exit codes keep the daemon stopped or
  `unmount` refuses and names the service command. Decide in this task from the probe's result.
- Double start: `autostart enable` and `service install` refuse while the other is set for the profile; `doctor` reports a
  conflict.

**Outcome (D093):** the daemon is told by `mount --foreground --service openrc|systemd`, and a plain `unmount` then refuses
and names the stop command; `unmount --force` still works. `--notify-fd <n>` (n at least 3), `$NOTIFY_SOCKET` and
`--clear-stale` as specified. `crates/pdmount/src/supervise.rs` holds the helpers M5.4 and M5.5 reuse: `Manager`,
`Manager::stop_command`, `openrc_service_link`, `systemd_unit_template`, `installed_service`,
`refuse_service_over_autostart` (for `service install`), `double_start`. The test is `tests/scenarios/svc.sh`.

## M5.4 and M5.5: `pdmount service`

`pdmount service [install|uninstall]`, without an argument the state. It detects the manager (`/run/systemd/system`, then
`/run/openrc`), and `--manager openrc|systemd` overrides that. It installs for `--profile`, with the secret-storage flag as
`autostart` does.

| | OpenRC | systemd |
|---|---|---|
| Files | `~/.config/rc/init.d/pdmount`, link `pdmount.<profile>` | `~/.config/systemd/user/pdmount@.service` |
| Enable | `rc-update --user add pdmount.<profile> default` | `systemctl --user enable --now pdmount@<profile>` |
| Run | `supervise-daemon`, `command_args="… -v mount --foreground --service openrc --clear-stale --notify-fd 3"` | `Type=notify`, `ExecStart=… -v mount --foreground --service systemd --clear-stale` |
| Restart | `respawn_max`, `respawn_period` | `Restart=on-failure`, `RestartSec=5` |
| Stop | `retry="TERM/<grace+30>/KILL/5"` | `TimeoutStopSec=<grace+30>`, `ExecStopPost=-<binary> --profile %i unmount --if-stale <mnt>` (D094) |
| Bus | `need dbus`, exports `DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus` | from the user manager; `After=dbus.socket dbus.service` (D091: the bus outlives the daemon) |

- The stop timeout is written at install from the configured grace; `doctor` warns when the unit and the config differ.
- D091: on OpenRC, `service install` prints the root drop-in that raises elogind's `InhibitDelayMaxSec` to the grace
  (`/etc/elogind/logind.conf.d/`), and `doctor` warns when the limit is below the grace. On systemd, `doctor` warns when the
  grace + 30 s exceeds the stop timeout of `user@.service` (120 s on Debian).
- A keyring still locked when the service starts must end in the existing `needs_login` path with its notification
  (D024, D042), never in a hang. Test by hand in M5.6.
- Tests: golden files of both units, a parser check with `openrc-run` syntax where installed, install and uninstall in a
  temporary `XDG_CONFIG_HOME` with stub `rc-update` and `systemctl`. The sandbox user has no session, so starting them is
  M5.6.

**Outcome of M5.4 and M5.5 (D094):** `crates/pdmount/src/service.rs`. Beyond the table: the profile's settings (secret flag, `retry`, log)
are in `rc/conf.d/pdmount.<profile>`, which OpenRC sources before the shared script, and for systemd in the drop-in
`pdmount@<profile>.service.d/pdmount.conf` (`Environment=PDMOUNT_SECRETS`, `TimeoutStopSec`, `ExecStopPost` with the mountpoint); `install` also starts the service
(`rc-service … start`) and `uninstall` stops it first; the output goes to the profile's log file; `doctor` reads elogind's
files and `user@.service`'s. Tests: `crates/pdmount/tests/service.rs` (stubs on `PATH`) and the unit tests with golden files in
`crates/pdmount/tests/golden/`.

## M5.6: Manual runs

A checklist (`docs/plans/m5.md`, below this section when run) for the user on Gentoo and Debian, on the fake with the
network profile so that no real-account limits apply, then once on the real account under `pdmount-test/` (D028, D030):
X5, a crash restart, a logout with an empty queue (no delay), a logout with a queue, a reboot with a queue, offline at
logout, a locked keyring at start.

### Running M5.6

As for the probe: on each system, logged in to the graphical session as the desktop user, no other session of that user
open, every command in a terminal inside that session. Part A runs a test build on a fake drive on disk with a slow
network profile, so nothing touches Proton; part B repeats a few cases on the real account under `pdmount-test/`.

`scripts/repro/m56.sh` runs part A: `setup`, then `run A<n>` per step (it writes the queue, marks the time and says
what to do), `check A<n>` after a logout or reboot (the log lines since the mark, status, service, the fake drive's
changes), `report` for the results to paste back, and `cleanup`. `m56.sh keyring` shows why the Secret Service does not
answer, before part B. The steps below are what it does.

**Build and install** (Gentoo: a clone of the repository as the desktop user; Debian: a clone of this repository's
`master`, copied or cloned over ssh, since M5 is not on GitHub yet):
- Debian needs `sudo apt install build-essential git clang libclang-dev protobuf-compiler pkg-config libdbus-1-dev fuse3`,
  Rust from rustup (1.89 or newer, for the locked dependencies) and Go 1.23 or newer (Debian 12's `golang` is too old:
  bookworm-backports or the go.dev tarball). `scripts/build-doctor.sh` checks all of these, and that the SDK fork and the
  Go modules can be downloaded.
- `cargo build --release -p pdmount --features fake-backend`, then
  `install -Dm755 target/release/pdmount ~/.local/bin/pdmount` (`~/.local/bin` on `PATH`). `pdmount --version` says 0.5.0.

**Part A setup: profile `m56` on a fake drive.**
1. `~/.config/pdmount/m56.toml`:
   ```toml
   mountpoint = "~/PdMount-m56"
   [device]
   name = "m56-gentoo"            # m56-debian on Debian
   [timeouts]
   shutdown_grace = "90s"
   ```
2. `mkdir -p ~/.local/share/pdmount-m56-fake` and `pdmount fake profile --rtt 80 --up 500000
   ~/.local/share/pdmount-m56-fake` (0.5 MB/s up: a 30 MB file takes about a minute, a 100 MB file longer than the grace).
3. `pdmount --profile m56 service install --backend fake:$HOME/.local/share/pdmount-m56-fake`.
   - Gentoo: `install` prints a file for root, `/etc/elogind/logind.conf.d/pdmount.conf`. Create it as root and reboot
     once; elogind reads it at boot.
   - Debian: `systemd-analyze --user verify ~/.config/systemd/user/pdmount@.service` (never run on the development
     machine). It should print nothing.
4. `pdmount --profile m56 doctor`: no warning on the service lines (Gentoo after the reboot). `pdmount --profile m56
   service` names the manager and the fake backend.

Where the log is: Gentoo `~/.local/state/pdmount/m56.log`; Debian `journalctl --user -u pdmount@m56` (`-b -1` for the
previous boot). For each step, note the time and keep the lines from that time on: the steps say which lines matter.

**Part A runs** (each `queue N` means `head -c N /dev/urandom > ~/PdMount-m56/qN-$(date +%s).bin`; `pdmount --profile m56
status` shows the queue):

| # | Step | Expected |

| A2 | Crash restart: `pkill -KILL -f 'pdmount --profile m56'`, wait 15 s, `ls ~/PdMount-m56` | the service restarts it within about 10 s; the log shows the stale mount removed (`--clear-stale`); the listing works |

## M5.7: Pending marker (D076)

When the grace ends with a non-empty barrier, the daemon uploads
`<root>/.pdmount/<device.id>.pending` directly through the backend, not the journal, in the last 10 s of the grace. It holds
JSON: device name, time, entries left, bytes left; no file names. It is trashed after the next drain. A reader shows
`Incoming:` in `status`, and a notification. Writing is opt-in (`sync.pending_marker`); reading is always on. The mount
exposes `.pdmount` read-only. Tests on the fake only: two daemons on one drive; a real-account run needs the user's
exception to D028, because the path is outside `pdmount-test/`.

The code goes in the engine, per tree, so that M5.14 needs no marker code of its own: `<root>` is the engine's tree root and the
counts are that engine's entries. Until M5.14 only My Files has a writable tree.

**Outcome (2026-11-12):** built as specified; the open details are D096 (accepted 2026-11-13): the marker is written when the barrier is
still moving 10 s before the deadline and the flush goes on after it, a watcher trashes it at any empty queue (also in the same
run), JSON version 1 with a 4 KiB one-block cap, one notification per marker revision remembered in the store, `.pdmount`
reserved in the root even before it exists. Code: `crates/pdmount-core/src/engine/marker.rs` (`Engine::leave_pending_marker`,
the reader and the drain watcher), `crates/pdmount/src/flush.rs`, `crates/pdmount/src/incoming.rs`; scenario
`tests/scenarios/x12.sh` (X12). For M5.14: `flush.rs` calls one engine; several trees need the 10 s point and the marker per

## M5.10: Several roots in one daemon

The shape that M5.11, M5.12 and M5.14 rest on (D080). **A tree is the unit, and the engine does not change for it:**

- **Tree:** volume, root link, writability. `ProtonBackend` already holds one volume and one root and builds every node id from them
  (`with_root` exists), so a further tree is another backend value. The SDK finds the signing address from each node's share by
  itself (`get_membership_address`), so shares need no signing code in PdMount.
- **Engine per tree:** one engine, with store, journal, staging and conflicts, per tree, over the one session and limiter. Nothing in
  the engine knows which kind of tree it serves. My Files is the first tree, with its paths unchanged.
- **Write gate:** one read-only flag per tree, checked where the D019 access rules are, and it can change at runtime. In this task
  and M5.11–M5.13 every further tree has it closed, but the full write path sits behind it.
- **Router:** a mount with several trees (Computers, Shared) has a virtual read-only top level with one folder per tree, and the
  FUSE layer maps inode numbers to their tree. A mount with one tree has no router, so My Files keeps its direct path.
- **One poller per volume:** it hands event pages to the trees of that volume. Computers shares My Files' volume, and two
  engines polling it would double the traffic (`cs/README.md`). Other users' volumes poll every 10 min, and the one whose share was used last through the mount every 30 s (D107, as the
  current official client); a core `DriveShareRefresh` event (30 s) re-reads the shared-with-me listing and the share roots (M5.9).
- **Bulk-read guard (D081):** works per session, so it covers every tree, My Files included. When many different files are opened in
  quick succession, as a thumbnailer or a recursive `grep` does, their reads become a scan: below interactive priority, paced like
  other background work, with no readahead and a limit on the share of the block cache they may use. A read that continues past the
  first blocks of a file, or a file opened while no scan runs, stays interactive, so opening a photo stays fast. Thresholds come from
  M5.9's measurements; check that `rsync` and `git` on My Files stay within the M4 benchmarks, since they open many files too.

`[[roots]]` config (kind, mountpoint; add to Appendix B). `Backend::root()` and `poll_events` move to the tree and poller; the fake
gets several volumes and members with roles. `status`, `unmount` and `mount -o ro` work per mount, and one tree failing does not
stop another. Tests: mounted fake tests with a second tree running the write scenarios with the gate forced open (so the shape
is proven here, not in M5.14), and the My Files scenarios unchanged.

## M5.14: Read-write (D080)

Opens the gate. No new write path: journal, staging, conflicts, fsync modes, `.pdignore` and flush are the ones My Files uses.

1. **Gate:** Computers open. Shares open when the role from the node is `Editor` or `Admin`; `Viewer` stays EROFS (D019). The role is
   read at listing and re-read when M5.9's signal says it changed.
2. **Losing the right, with changes pending:** a permission error (`is_permission_denied`, code 2011 or HTTP 403) or a revoked share
   parks the tree's entries and closes its gate. Nothing staged is deleted (RQ3): the files stay readable in the mount while
   possible, and then go to `~/.local/share/pdmount/<profile>/orphaned/<tree>/` with a notification and a line in `status`.
3. **Across trees:** rename between trees returns EXDEV, so `mv`, `rsync` and `git` copy instead. Every tree counts as its own
   filesystem for this.
4. **Quota:** an upload to a share counts against the owner's storage. The server's error maps to ENOSPC as it does in My Files, but
   `df` on the mount shows the user's own quota, so a full share appears only as that error. Document it.
5. **Marker (D076):** each writable tree with entries left gets its own in its root, counting only that tree's entries. Opt-in per
   root (`pending_marker` under `[[roots]]`), so writing into shares is its own choice; in a share it leaves out the device name.
   The trees share the last 10 s of the grace, so some may get no marker. Test: A, an `Editor`, runs out of grace; B, the owner on a
   second daemon, sees `Incoming:`; A's My Files gets no marker for those entries.
6. **Other clients:** a device's folder is usually being synced by the official client on that device, so writing there is a
   normal multi-device case (§10). Conflict copies in a share are visible to its other members. Document both.

## M5.17: The desktop's session bus for the service (D102)

Found in M5.6 on Gentoo: the desktop runs its own session bus (`dbus-launch`), and moving the desktop onto the OpenRC user
bus breaks udisks mounting (Results: Gentoo). So the desktop tells the service which bus it has, at every login:

- **Install:** `service install` also writes `$XDG_CONFIG_HOME/autostart/pdmount-<profile>-attach.desktop`, which runs
  `pdmount --profile <p> session attach` (the binary and profile as for the service; no secret flag needed); `uninstall`
  removes it. The file name differs from the autostart entry's (`autostart.rs` `entry_path`), so `autostart` and the
  "service and autostart both" check (D093) do not count it. Reuse the `.desktop` writer of `autostart.rs`.
- **`session attach`:** reads `DBUS_SESSION_BUS_ADDRESS` and sends a new control request `AttachBus { address }`. No
  daemon: exit 0, one line. The daemon compares the bus ID (`org.freedesktop.DBus.GetId`, zbus, 2 s) with its own bus's:
  equal, nothing changes (the usual systemd case); different, it keeps the address and logs it at INFO; unreachable,
  refused with the error. Accepts only `unix:path=` and `unix:abstract=` addresses.
- **Notifications** (`notify.rs`): `notify-send` gets the attached address through `Command::env`; `available()` holds
  when an address is attached or the process has one.
- **Keyring** (`credentials.rs`): `keyring` and `dbus-secret-service` take the bus from the environment only, and the
  daemon may not change its own environment. With an address attached, `OsKeyring`'s get/set/delete and
  `keyring_state` run in a child, a hidden `pdmount keyring-helper` subcommand, with the address in its environment; key
  and value pass over stdin and stdout, never argv (D071). The child is run under `with_keyring_timeout` (it is killed
  at the timeout). An attach resets the unavailable flag (`retry_keyring`).
- **Logout:** a failed call on the attached bus (gone, no reply) drops the address; later calls use the daemon's own bus
  until the next attach.
- **Finding 6, start without a keyring:** a daemon of a profile that was mounted before (stored root) does not exit when
  the keyring is unavailable at start. It waits, logs once, and retries at an attach, at `pdmount login`, and every 60 s;
  `status` shows `needs_login` with the reason meanwhile. To decide in the task: the cache master key also comes from the
  keyring (`daemon.rs`, the cache key load), so either the mount waits for it (readiness is reported only then; the
  supervisor's start timeout must allow it) or it mounts with the RAM cache only and opens the disk cache once the key
  arrives. Either way no exit, so no respawn (finding 5's B2 case).
- **`doctor`** (with M5.16): for an installed service, "desktop bus: same as the service's / attached / not attached".

Tests: `notify.rs` with a stub `notify-send` that records its environment; the helper against a private `dbus-daemon`
with gnome-keyring (as `scripts/repro/keyring-d024.sh`); install/uninstall of the attach entry with the stubs of
`crates/pdmount/tests/service.rs`; a mounted fake test with two private buses: a daemon on bus A, `session attach` from
bus B, a notification and a keyring read land on B; the start without a keyring (finding 6). Full CI. The user reruns on
